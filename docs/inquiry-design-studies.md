# Inquiry：新しい見せ方の比較

## 狙いと前提

Iconv2の主体の判別しやすさを残し、商談で「何がどう作用するか」を比較できる3案を作る。
既存と同じ24秒・30fps・1920×1080、6工程。実装済みアプリの画面ではなくInquiry構想の説明。
LINE / Gmailは既存の公式素材、その他は役割ピクトグラムを使う。元のコンポジションは変更しない。

検討した方向は路線図、放射状ネットワーク、受け渡し舞台、担当別スイムレーン、縦の監査記録、等角投影。
担当別レーンと監査記録は説明資料寄り、等角投影は意味のない奥行きが増えるため、今回は前三者を実装する。

| 案 | 主役 | 作用の見せ方 | 確認したい点 |
|---|---|---|---|
| Transit | 全体の経路 | 一つの情報パケットが路線を走る。参照・任意経路は破線 | 明るい画面で分岐と戻りを追えるか |
| Orbit | データと判断の往復 | 中心の判定と周囲の主体を接続、受信側にリング | 線形フローで見えにくい依存関係が伝わるか |
| Relay | その瞬間の受け渡し | 送信側→情報→受信側を大きく提示、工程内でも送り手が交代 | 何が渡ったかを初見で理解できるか |

## 受入条件・実装手順

- 新規フォルダ `src/agent-flow/inquiry/design-studies/` とRootへの追加だけで実装する。
- 既存の11主体・13接続（双方向の判定、業者マスタ参照、任意承認、一次回答、改善）を維持。
- 人は判断基準を調整し、次の判定で参照される。AIを直接書き換える演出にしない。
- 既存と同じく下書き承認の経路を例示し、自動送信の条件や実装を創作しない。
- フレームだけで状態と動作を決定し、参照・非同期・任意の意味を凡例に残す。
- Transit/Orbitは全経路を常設。Relayは全接続を時系列に提示する説明映像で、全体図ではない。
- 型検査→各工程の静止画→動作プレビュー→ギャラリー更新の順で確認。

コマンド: `pnpm exec tsc --noEmit`、`pnpm gallery:agent-flow`。
動画: `pnpm exec remotion render Inquiry-Transit out/inquiry-design-studies/Transit.mp4 --gl=swangle --image-format=png --pixel-format=yuv420p`。
他の案はIDを `Inquiry-Orbit` / `Inquiry-Relay` に変更。

## 実装したもの

- Studio: `AgentFlow > Inquiry > DesignStudies` に `Inquiry-Transit` / `Inquiry-Orbit` / `Inquiry-Relay`。
- 3案は同じ11主体・13接続を共有。既存の接続定義から情報の受け渡しを導き、意味の相違を防ぐ。
- 各工程内の接続を順に見せるため、動画全体は24秒のまま。
  業者連絡は4つの受け渡しを4秒で示すので、詳しく説明する商談では停止・シークを使う。
- Transitは角丸の駅と3本の帯、Orbitは円形主体と中心の判断、Relayは大きい主体と移動する情報票。
- アイコンやロゴ自体を変形させず、外側の輪と移動パケットで送受信を表す。
- 座標は `model.ts` のレイアウトを共用し、線の端点もそこから導出。

## 比較の見立て

現時点の推奨は **Transit**。全体経路を保ったまま、明るい会議室でも主体を読み分けやすい。
**Relay** は初見の相手に「具体的に何をしているか」を説明する導入に向く。
**Orbit** はAI判定の往復と改善の環を主張したい場合の案。初見ではTransitより順序を追いにくい。
これらはプロトタイプを見た設計上の判断で、ユーザー検証は未実施。

## 追加の3案（第2ラウンド）

前回と同じ主体・接続・24秒を使い、「全体図」「受け渡しの舞台」以外の見方を追加した。
既存の3案や共通の接続定義は変更していない。

| 案 | 配置と動き | 向いている説明 |
|---|---|---|
| Lanes | 外部チャネル／エージェント／人・参照情報の3レーン。現在の受け渡しだけをレーン間に描く | 自動処理と人の関与の境界を説明する |
| Chronicle | 13の受け渡しを縦に並べ、進行に合わせてスクロール。右に現在の情報を大きく表示 | 順番に追いながら途中で止めて説明する |
| Caseboard | 中央の案件カードに工程の情報が揃い、周囲の主体が近づく。送り手と受け手の線を順に流す | 1件の問い合わせを複数の主体で進めることを伝える |

### 表現上の境界

- Lanesは全体経路図ではなく、担当別の受け渡しビュー。13接続を時間順に提示する。
  「人・参照情報」は担当者と参照データを同じ帯に置く分類であり、データが人であることは意味しない。
- Chronicleは処理順の説明。実アプリの監査ログ・時刻・永続化の保証を表すものではない。
- Caseboardのカードは表示用のまとめ。既存構造に新しい保存先や処理ノードを加えたものではない。
- 3案とも業者連絡は下書き承認の経路を例示。判断基準を人が調整し、次の判定で参照する関係を維持。

## 第3追加案: Branches / Terraces

- **Branches**: 暗いチャコールに銅色と青緑の2つの到達先。太い帯は「手配」「回答」の成果のまとまりを示し、実際の13接続は現在の矢印で順に表示する。データ化への判断の返却も維持。下部に人による改善と参照情報を置く。
- **Terraces**: 理解・伝達・判断支援を3つの段に分ける。主体は正面向きのアイコンを維持し、受け渡し時だけ少し浮く。奥行きは役割の区分に限定し、システム構成や実際の上下関係を示さない旨を表示する。

両案ともInquiry既存の11主体・13接続・6工程を維持し、24秒 / 1920×1080 / 30fps。下書き時の人による承認、業者マスタの参照、人による判断基準の改善を区別する。静止画6枚とMP4を比較ページに追加し、AgentFlow一覧にも登録する。

- 既存6案のframe420が変更前PNGとバイト一致。Inquiry-IconsV2のframe360も一致。
- 2動画とも1920×1080、30fps、720フレーム、24秒、yuv420p。レンダリング前後のソースSHA一致。
- 比較ページの全8動画の読み込み・14秒へのシーク、56画像の読み込みと縦横比を確認。1440px・390pxで横はみ出しなし。
