## 1. 対象スコープ

今回図にするのは、問い合わせが入ってから一次回答が返るまでと、その判定を継続的に良くする部分。

```
Line で問合せ受付 -> データ化
データ化 <- AIによる優先度/初期対応方針の決定
  * AIの判定に対して人がフィードバックを入れて改善サイクル
データ化 -> 業者マスタを参照して、自動連絡(or下書き) -> Gmail, Line
  -> 問い合わせに対するユーザーへの一次回答
```

見積依頼・見積比較・発注承認・完了確認は、この先のスコープとして別途追加する。

## 2. 論理構造

```
 入居者 ──①受付──▶ ②データ化 ──────▶ ④業者連絡 ┄┄▶ [承認] ┄┄▶ 業者
   ▲                 ▲   │                ▲         (任意)     (Gmail/LINE)
   │                 │   │ データ          ┆ 参照
   │          判定結果 │   ▼                ┆
   │                 ③AI判定           業者マスタ
   │                   ▲   │
   │                   ┆   │ 判定結果を見る
   └──⑤一次回答─────────┆───┘
                       ┆ 参照
              ルール・コンテキスト
                       ▲
                       │ 調整
                    担当者
```

構造上のポイントは4つ。

1. **②データ化がハブ**。左から入り、③AI判定へ降り、④業者連絡へ抜ける。要件の「データ化 ← AI判定」は双方向エッジ（データを渡す／判定結果を書き戻す）で表現する
2. **改善サイクルは3ノードの閉ループ**。担当者がAIを直接直すのではなく、`ルール・コンテキスト` という成果物を調整し、③AI判定がそれを参照する。これによって「次の問い合わせから効く」という時間差が図に出る
3. **⑤一次回答が入居者に戻る**ので、ループの継ぎ目が自然に閉じる（①の始点と⑤の終点が同じカード）
4. **業者への送信前の承認は任意ゲート**。要件の「自動連絡(or下書き)」を、点線のノードとして④と業者のあいだに置く（§4.1）

## 3. 画面レイアウト（1920x1080）

```
[StepBar ①受付 ②データ化 ③AI判定 ④業者連絡 ⑤一次回答 ⑥改善]        [Legend]

         ┌──────────── FARLEAP / INQUIRY RUNTIME ───────────┐
 ┌──────┐│ ┌────────┐   ┌──────────┐   ┌──────────┐        │ ┌ ─ ─ ┐  ┌──────┐
 │入居者 ├┼▶│①受付   │──▶│②データ化 │──▶│④業者連絡 ├┄┄┄┄┄┄┼▶│承認 │┄▶│業者   │
 │ LINE │ │ └────────┘   └────┬─────┘   └────▲─────┘        │ │(任意)│  │Gmail │
 └──────┘│                   │▲             ┆参照          │ └ ─ ─ ┘  └──────┘
    ▲    │ ┌────────┐   ┌────▼┴────┐        ┆               │
    └────┼─┤⑤一次回答│◀──┤③AI判定   │        ┆               │
         │ └────────┘   └────▲─────┘        ┆               │
         │                   ┆参照          ┆               │
         │              ┌──────────┐   ┌──────────┐         │
         │              │判断基準   │   │業者マスタ │         │
         │              └────▲─────┘   └──────────┘         │
         └───────────────────┼──────────────────────────────┘
                             │調整
                        ┌──────────┐
                        │ 担当者    │
                        └──────────┘
```

- 枠の外に置くのは「人」と「外部サービス」のみ（入居者・担当者・業者・承認ゲート）。既存 `AgentFlow` の「人は枠の外」ルールを踏襲する
- 承認ゲートは④と業者を結ぶ**水平線の上**に置く（枠の右、業者の手前）。下へ迂回させる案も試したが、線が上下するぶん読みづらく、左から右に読む本線の流れも切れるため、一直線上のチェックポイントにした
- 3行目は「参照データ層」。判断基準と業者マスタを並べると、どちらも「参照されるだけで自分からは動かないもの」という共通性が位置で伝わる。業者マスタから④への線は空いた2行目を縦に抜ける
- ノードサイズは 208x116（任意ゲートのみ 168x92）。ノードが11個あるので、既存 `AgentFlow` の 340x260 から大きく縮めた。見出し25px、補足12.5px、英字ラベル11px
- `ルール・コンテキスト` は枠の内側の最下段に置く。人（枠外）とAI（枠内）の境界に接する位置になり、「人の意図がシステムに入る接点」という意味が位置で伝わる
- 改善サイクルの2本（③から担当者へ降りる線、担当者からルールへ上がる線）は、`AgentFlowCodexReClaude` の `human-in` / `human-out` と同じく平行に並走させる

## 4. ノード定義

内部ノード7個、外部ノード3個。

| # | 日本語 | 英字ラベル | 補足テキスト | 内/外 | アイコン |
|---|---|---|---|---|---|
| ① | 受付 | LINE WEBHOOK | 写真つきで相談が届く | 内 | message |
| ② | データ化 | NORMALIZE | 物件・症状・緊急度に分解 | 内 | branch |
| ③ | AI判定 | TRIAGE | 優先度と初期対応方針を決める | 内 | agent |
| ④ | 業者連絡 | DISPATCH | 自動送信 または 下書き | 内 | phone |
| ⑤ | 一次回答 | REPLY | 入居者へLINEで返す | 内 | message |
| — | ルール・コンテキスト | POLICY & CONTEXT | 優先度の基準、物件ごとの事情 | 内 | tool |
| — | 業者マスタ | VENDOR DB | 対応エリア・得意分野 | 内 | database |
| — | 入居者 | LINE | 起点かつ終点 | 外 | people |
| — | 業者 | GMAIL / LINE | 送信先 | 外 | tool |
| — | 担当者 | HUMAN REVIEW | 判定を見て、ルールを調整 | 外 | check |
| — | 承認（任意） | DRAFT APPROVAL | 下書きのときだけ担当者が確認 | 外 | check |

`ルール・コンテキスト` ノードの文言は、「人がAIを直接直している」ように読ませないことを優先する。

- 小ラベル: `ルール・コンテキスト`
- 大見出し: `判断基準`
- 補足: `担当者が調整` / `次の判定に効く`

アイコンは `ServiceIcon` の既存10種から割り当てた。`message` `tool` `check` が2回ずつ使われるので、
区別したい場合は `inbox`（受付用）と `wrench`（業者用）あたりを追加する。

### 4.1 「任意」の表現ルール

要件の `自動連絡(or下書き)` は、モードによって人の確認が入ったり入らなかったりする。
これを「必ず通る工程」と同じ見た目にすると嘘になるので、任意であることを見た目で区別する。

| 項目 | 必須ノード | 任意ノード（承認ゲート） |
|---|---|---|
| 枠線 | 実線 2px | **破線** 2px（`stroke-dasharray`） |
| サイズ | 通常（`IconNode` 標準） | ひと回り小さいチップ |
| 小ラベル | 役割名 | `下書きのときだけ` |
| 出入りのエッジ | 実線 | **破線** |
| アクティブ時 | 系統色ではっきり光る | 破線のまま淡く光る（実線ノードほど強くしない） |

アクティブ時の光り方に差をつけるのが重要で、④のビートで本線が流れるときに承認ゲートだけ控えめに反応させると、
「通ることもあるが、必ずではない」が伝わる。

ルートは1本にする。「自動送信の直行ルート」と「承認を経由するルート」を2本並べる案もあるが、
線が増えるわりに読み取れる情報が増えないため、破線ゲートを1本通す形に寄せる。

## 5. エッジ定義

| from → to | 意味 | 色 | 線種 |
|---|---|---|---|
| 入居者 → ①受付 | 問い合わせが届く | シアン | 実線 |
| ①受付 → ②データ化 | 会話・写真を渡す | シアン | 実線 |
| ②データ化 → ③AI判定 | 判定にかける | バイオレット | 実線 |
| ③AI判定 → ②データ化 | 優先度・方針を書き戻す | バイオレット | 実線 |
| ②データ化 → ④業者連絡 | 手配に回す | バイオレット | 実線 |
| 業者マスタ → ④業者連絡 | 業者を引き当てる | グレー | 破線 |
| ④業者連絡 → 承認 | 下書きなら確認に回す | グリーン | 破線（任意） |
| 承認 → 業者 | Gmail/LINEで送る | グリーン | 破線（任意） |
| ③AI判定 → ⑤一次回答 | 方針をもとに返信文 | バイオレット | 実線 |
| ⑤一次回答 → 入居者 | LINEで一次回答 | グリーン | 実線 |
| ③AI判定 → 担当者 | 判定結果をレビュー | オレンジ | 破線 |
| 担当者 → ルール・コンテキスト | 基準と文脈を調整 | オレンジ | 実線 |
| ルール・コンテキスト → ③AI判定 | 次の判定が参照する | オレンジ | 破線 |

## 6. 配色・線種

既存 `AgentFlow` の凡例構造（4分類＋破線は流れない線）を踏襲する。

| 意味 | 色 | 使う場所 |
|---|---|---|
| 入力（人からシステムへ） | シアン `#22D3EE` | 入居者→①→② |
| AIの判断 | バイオレット `#8B5CF6` | ②⇄③、②→④、③→⑤ |
| 人の介在 | オレンジ `#FF6B1A` | ③⇢担当者→ルール⇢③ |
| 送信・外部連携 | グリーン `#34D399` | ④→業者、⑤→入居者 |
| 参照 | グレー `#3A4756` | 業者マスタ⇢④ |

破線は3つの意味に使う。実線は「その場で必ず流れるデータ」に限る。

| 破線の用途 | 例 |
|---|---|
| 参照（流れない） | 業者マスタ ⇢ ④、ルール・コンテキスト ⇢ ③ |
| 非同期のフィードバック | ③ ⇢ 担当者 |
| **任意（通らないことがある）** | ④ ⇢ 承認 ⇢ 業者 |

3つとも破線なので、色で区別する（参照はグレー、フィードバックはオレンジ、任意はグリーン）。
凡例には破線の意味を1行足すか、任意ゲートのノード側ラベル（`下書きのときだけ`）に説明を寄せる。

## 7. タイムライン（6ステップ x 4秒 = 24秒 / 720フレーム）

| step | 秒 | 光るノード | 流れるエッジ |
|---|---|---|---|
| ① 受付 | 0-4 | 入居者、①受付 | 入居者 → ① |
| ② データ化 | 4-8 | ②データ化 | ① → ② |
| ③ AI判定 | 8-12 | ③AI判定 | ② ⇄ ③ |
| ④ 業者連絡 | 12-16 | ④業者連絡、業者マスタ、業者（承認ゲートは淡く） | ② → ④、マスタ ⇢ ④、④ ⇢ 承認 ⇢ 業者 |
| ⑤ 一次回答 | 16-20 | ⑤一次回答、入居者 | ③ → ⑤ → 入居者 |
| ⑥ 改善サイクル | 20-24 | 担当者、ルール・コンテキスト、③AI判定 | ③ ⇢ 担当者 → ルール ⇢ ③ |

改善サイクルを最後のビートに置く理由は2つ。

- 本線（受付から一次回答まで）が先に完結するので、話の筋が通る
- 最後に「次はもっと良くなる」で終わってから①に戻るため、ループ1周が「1件の処理 + 1回の改善」として読める

実際の改善サイクルは非同期に起きるので、順番に並べるのは図としての都合。
ステップ数を5に抑えたい場合は、⑥を③に内包して常時ゆっくり脈打たせる案もある。

## 9. 決定事項

| 項目 | 決定 |
|---|---|
| 一次回答の起点 | ③AI判定から。AIの初期対応方針がそのまま返信文のもとになる |
| 下書き承認 | 任意ゲートとして④と業者のあいだに置く。破線ノードで「通らないことがある」を表す（§4.1） |
| ステップ数 | 6ステップ x 4秒 = 24秒（720フレーム） |
| ノード表現 | `IconNode` で統一。ノードが10個あり、大きい `NodeCard` では収まらない |
| `StepBar` | ステップ数に依存しない形へ一般化してから使う |

## 10. 実装メモ

| ファイル | 内容 |
|---|---|
| `src/AgentFlowInquiry/constants.ts` | グリッド、ノード11個、エッジ13本、配色、タイムライン |
| `src/AgentFlowInquiry/index.tsx` | 図の描画、直角ルーティング、ステップバー、凡例、進捗バー |

- ノード座標もエッジ経由点も、すべて列（`COL_A/B/C`）と行（`ROW_1/2/3`）の定数から導出している。`AgentFlowCodexReClaude` のリファクタで得た「座標を2箇所に書かない」を最初から適用した
- `ServiceIcon` に `inbox`（受付）と `sliders`（判断基準）を追加した。これで重複は「入居者と一次回答がどちらも `message`」だけになるが、どちらもLINEの会話を指すので意図どおり
- `StepBar` はこのコンポジション内に実装し、`STEPS.length` から段数を決める。ステップ数を変えてもコードは変わらない
- エッジ描画（角丸折れ線、進行ドット、流れる破線）は `AgentFlowInquiry` 内にローカル実装した。`AgentFlowCodexReClaude` の `EdgeLine` は向こうのデータモデルに結合しているため。3つ目のフロー図を作るときは `src/shared/` へ切り出す
