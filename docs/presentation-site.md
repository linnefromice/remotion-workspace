# デモ用1枚サイト 検討メモ

作ったエージェントフロー図を使って、「実際に動いているところ」を想像させる1枚のサイトを作る、
という相談の検討記録。2026-09-17 時点。

## 1. なぜフロー図だけでは足りないか

フロー図は**三人称の俯瞰図**なので、構造的に映せないものがある。

| フロー図が語れること | 語れないこと |
|---|---|
| どこからどこへ流れるか | 当事者が何を見ているか |
| どの工程に人が挟まるか | その工程が何秒かかるか |
| ルールが昇格させること | 昇格しなかった場合に何が起きるか |

商談の主題が「AIが判定します」ではなく**「AIが間違えたときにどう担保するか」**である以上、
最後の行が一番効く。そこがフロー図の弱点と重なっている。

## 2. 方針: 同じ瞬間を「俯瞰」と「現場」で同時に見せる

フロー動画の進行に合わせ、同じステップの**現場**を横に出す。

| ステップ | 現場に出すもの |
|---|---|
| 受付 | 入居者のスマホ画面（LINEの実際の文面と写真） |
| 文字起こし | 音声から起こされたテキスト |
| AI判定 | AIの生出力そのもの `{"urgency":"P2","confidence":"medium"}` |
| ルール昇格 | 発火したルール名と、書き換わらず並ぶ2つの値 |
| 業務判断 | NextAction候補（ガードレールが足したものに印） |
| 人の確認 | 管理画面（P1バッジ・ルール昇格タグ・降格には理由） |
| 出口 | CSVの1行（`urgency_ai` と `fired_rule_ids` が並ぶ） |

**「AIがP2と言った」は抽象だが、JSONに `"P2"` と書いてあるのを見せると現実になる。**
これが狙いのすべて。

### 主役をどちらにするか

情報量が増えるので視線が散る。どちらかを主役にして、もう一方は従に倒す必要がある。

- **現場を主役、フロー図を小さく常時表示**（推奨）。フロー図は「今どこの話か」を示す地図として
  機能すれば足りる
- フロー図を主役にすると、現場が添え物になって具体性が出ない

ただし**既存のフロー図は1920x1080いっぱいを使う前提で文字サイズを決めている**ので、
縮小すると文字が読めなくなる。地図として使うなら、ノードとハイライトだけの簡略版を
別に用意するほうが素直かもしれない。仮置き版で実際に縮小して確認する（§4）。

## 3. 補強の候補

優先度順。

1. **反実仮想の2枚並べ**: 「ルールなし → P2のまま → 翌営業日対応」と
   「ルールあり → P1昇格 → 即時架電」。フロー図は仕組みを語れるが、
   **失敗したときの損失**を語れない。主題が担保である以上、これが一番刺さるはず
2. **経過時間**: 「受付から一次回答まで47秒」。速さは図では伝わらない
3. **触れる部分**: 定型文3つほどから選ぶと発火するルールが変わる程度の簡易なもの。
   「説明された」が「試した」に変わる

## 4. 仮置き版（2026-09-17）

まず**横に並べてみて成立するか**を見るための版を作った。
Studio の `AgentFlow > ClaimIntake > ClaimIntake-SideBySide`。

- 左: 既存の `AgentFlowClaimIntakeIcons` をそのまま縮小して配置（地図）
- 右: ステップに同期した現場パネル

作り方は「既存のコンポジションを `transform: scale()` で縮めて埋め込む」だけ。
`useCurrentFrame()` はそのまま効くので、同期のためのコードは要らない。

### 並べてみてわかったこと

全7ステップを書き出して確認した結果。

1. **縮小しても読める**。0.59倍まで縮めてもノード名は読めた。
   §2で懸念した「地図用の簡略版が要る」は、当面は不要そう
2. **左右で内容が重複する**。フロー図が持つ「判定の非対称」パネル（AI P2 / ルール P1 / 現在値 P1）と、
   右のステップ4がまったく同じことを言っている。**どちらかを削る必要がある**。
   左を地図に徹させるなら、埋め込み用にパネルを消した版を作るのが素直
3. **縦が余る**。16:9に左右2カラムを置くと、下の1/4が空く。
   §3の補強（反実仮想・経過時間）を入れる余地はここにある
4. 副産物として、埋め込み元の `ClaimIntake-IconsV2` で **LINEノードのラベルが重なっている**のを見つけた
   （「Webhook / 外部チャネル」の折り返しが下のタグにかぶる）。仮置き版では触っていない

視線移動については、左右で成立していた。上下に積む必要は感じない。

## 5. §4 の課題に当てた2案（2026-09-17）

§4-2（左右の重複）と §4-3（余った下部）に、それぞれ1つずつ当ててみた。
比べられるよう、別々のコンポジションに分けている。

### 案1: 左を地図に徹させる — `ClaimIntake-SideBySide-Map`

`AgentFlowClaimIntakeIcons` に `hidePanel` を足し、埋め込むときだけ
「判定の非対称」パネルを出さないようにした。

- 左右で同じ値（AI P2 / ルール P1）を2回言う状態が解消され、
  右の「発火したルール」が唯一の主張になった
- 代わりにフロー図の左下が空く。地図としては困らないが、枠内が少し寂しい

既存の4コンポジション（Icons / IconsV2 / LogoSeal / ActionRow）は
16フレームでバイト一致を確認済み。`hidePanel` の既定は false。

### 案2: 下段に反実仮想を置く — `ClaimIntake-SideBySide-Counterfactual`

§3-1 の2枚並べを、余っていた下段に帯として入れた。

| | 結末 |
|---|---|
| ルールが無い場合 | AIのP2のまま → 翌営業日に手配 → ガスのにおいは誰も見ない |
| ルールがある場合 | P1へ昇格 → 即時架電・当日手配 → 47秒で一次回答 |

ステップ4（ルール昇格）から「ある場合」だけが点灯する。それまではどちらも中立。
**空いていた場所にちょうど収まる**ので、レイアウトを崩さずに足せた。

### 比べてみて

2案は競合しないので、**最終版は両方入れるのが素直**だと思う。
案2だけだと左のパネルと下段の帯がどちらも「ルールが効いた」話をしていて、
言いたいことが3箇所に散る。案1で左を黙らせてから案2を足すのが順番として正しい。

## 6. 案3: 追記タイムライン — `ClaimIntake-SideBySide-Timeline`（2026-09-17）

経過時間（§3-2）と、inquiry_events の追記（§2の題材の芯）を別々に作ろうとしたが、
**1920x1080 に左右2カラムを置くと、縦に積める余地が下の1帯ぶんしかない**。
横軸を時間にしてイベントを左から積む形にすると、同じ場所で両方言える。

- 速さ（受付から47秒）は、目盛りの詰まり方で見える。実際、0〜22秒に6件が固まり、
  そこから47秒まで空く。**待ち時間がどこにあるか**が図になった
- 追記のみ（消えない）は、一度出た点が最後まで残ることで見える

`counterfactual` と場所を取り合うので排他にしてある。

あわせて、案1+案2＋経過時計の組み合わせを `full` として用意した。
`zod` スキーマを付けたので、Studio の props パネルから他の組み合わせも試せる。

### 足すたびに起きたこと

**同じ数字を3箇所で言ってしまう。** 「47秒」が時計・現場（出口）・反実仮想で重複した。
フラグで抑制したが、要素を足すたびに「既にどこかで言っていないか」の確認が要る。

## 8. 判断記録を主役にする案（2026-09-17）

### 設計・受入条件

商談での問い「AIが間違えたら？」への答えを、1件の記録が積まれていく28秒の
動画 `ClaimIntake-DecisionStory` にする。設計から委任されたプロトタイプとして進める。
横並びの俯瞰図より、通報文 → AI原判定 → 安全ルール → 担当者 → 記録を大きく見せる。
フローの全体像は既存案で補完する。本案は経路図ではなく、案件の判断記録である。

- 1920×1080、30fps、840フレーム、120フレームごとの7工程。
- AIのP2とルールのP1を別の欄に保持。ルールは白、AIは紫、人は青で表示。
- 反実仮想は「比較用の仮定」。危険の発生や見落としの結果を断定しない。
- 47秒はシナリオ値であり、実測・性能保証ではない。途中の秒数は創作しない。
- 降格は人のみ・理由必須という権限を説明し、架空の降格実績は作らない。
- schema/defaultProps で比較欄の表示を切り替える。
- 既存ソースはRootの追加登録以外変更しない。依存追加・外部接続なし。

### 実装と検証手順

1. `src/ClaimIntakeDecisionStory/index.tsx` にフレーム由来の表示を実装、Rootに登録。
   既存同様 `React.FC<z.infer<typeof schema>>` とインラインスタイルを使う。
2. `pnpm exec tsc --noEmit` で型検査。
3. 60,180,300,420,540,660,780のPNGを出力して目視。
4. 既存IconsV2の420フレームを変更前後でPNGバイト比較。レンダー前後にソースハッシュ確認。
5. `pnpm exec remotion render ClaimIntake-DecisionStory out/decision-story/demo.mp4 --gl=swangle --image-format=png --pixel-format=yuv420p`。

常に行う: シナリオと仮定の明示、既存出力の保持、静止画検証。
別途相談する: PoC接続・実測値の主張・外部公開。禁止: AI値の上書き演出、実装未確認のルール創作。

### 検証結果・この案の限界

- 型検査成功。7工程の中間フレームを目視し、判断カード末尾の余白を修正して再確認。
- `showComparison: false` も420フレームで確認。比較の代わりに原値保存の説明を出す。
- 既存 `ClaimIntake-IconsV2` の420フレームは変更前後で `cmp` 一致。
  既存コンポジションのソースは変更していない。他の全フレームの一致までは検査していない。
- 出力先: `out/decision-story/`（git対象外）。7枚のPNGと `demo.mp4`。
- Studio: `AgentFlow > ClaimIntake > ClaimIntake-DecisionStory`。
- 写真そのものと実アプリの管理画面は再現していない。写真は添付件数として扱う。
  今回は判断の相違と権限が伝わるかを検討する案で、操作できるサイトではない。
- 入力確認の工程は写真付きテキストのケースに合わせた。音声の文字起こしを行ったようには描かない。
- 比較帯と記録帯を時間で切り替えることで、既存案の「下段の場所の取り合い」を解消。
  その代わり、全体経路の把握は既存フロー案に任せる。商談で順に見せて比較できる。
