# [1] 題材の見つけ方

「どの業務にエージェントが効きそうか」を探し、**1枚のフロー図にできる形**まで持っていく手順。
図の描き方は [`agent-flow-diagram-patterns.md`](./agent-flow-diagram-patterns.md)（[2]）、
できた図を資料にするのは [`presentation-page-patterns.md`](./presentation-page-patterns.md)（[3]）。

この3本は鎖になっていて、**各段の出口が次の段の入口**になる。
この文書の出口は §5 の「引き渡し票」。

調査そのものを外部のLLMに頼むなら、そのまま貼れる依頼書が
[`agent-flow-research-prompts.md`](./agent-flow-research-prompts.md) にある。
業界別の当てどころは [`agent-flow-research-domains.md`](./agent-flow-research-domains.md)、
一度回してみた記録は [`agent-flow-research-example.md`](./agent-flow-research-example.md)。

## 0. どこから始めるか

手元に何があるかで入口が変わる。**上ほど嘘をつきにくい。**

| 手元にあるもの | 例 | 進み方 |
|---|---|---|
| **実装がある** | ClaimIntake（PoCのコードがある） | §1。コードを読んで**実装が既に持っている主張**を掘る |
| **語れる人がいる** | Inquiry（業務の説明を文章でもらった） | §2.1。語りを時系列に並べ直す |
| **業界だけ決まっている** | 「物流の現場で何かできないか」 | §2.2。事故・規程・困りごとを調べる |
| **何もない** | まっさらなブレスト | §2.3。想像。ただし歯止めをかける |

実装がある側が圧倒的に強い。**書けることが増えるのではなく、嘘を書けなくなる**から。
下に行くほど、票の §7（出典）で「どこまでが事実か」を明示する責任が重くなる。

## 1. 実装がある場合：コードから主張を掘る

探すのは機能ではなく、**設計者が何を守ろうとしたか**。次の4つを順に見る。

### (a) 型が分かれているところ

同じものに見えて別の型になっているなら、そこに主張がある。

> ClaimIntake では `Judgment`（AIの生出力・不変）と `ResolvedJudgment`（現在値）が
> 別の型だった。**「AIの出力を書き換えない」**という設計が型に出ていた。
> 図の主題はここで決まった。

### (b) 無い操作

CRUD のうち実装されていないものを探す。**無いことが主張**であることが多い。

> `inquiry_events` に update と delete が無い。追記のみ。
> ガードレールに「候補を削る」経路が無い。追加と制止だけ。

### (c) 非対称な権限

誰が何をできて、何をできないか。左右対称でないところが図の山場になる。

> 昇格はルールが強制できるが、降格は人しかできず理由が要る。
> **AIには降格の権限が無い。**

### (d) LLM を使っていないところ

AIの話なのに決定論で書かれている箇所は、たいてい「担保」のために意図的にそうなっている。

> セーフティルール5本は LLM を使わない決定論。だから図では
> AIでも人でもない第3の主体として立てた。

**(a)〜(d) で出たものを1文にまとめると、それが芯になる。**
ClaimIntake なら「AIが間違えたとき、どう担保するのか」。

## 2. 実装が無い場合

「実装がある」側は §1 で掘れる。無い側は、どこまで根拠があるかで3段ある。
**下に行くほど嘘をつきやすい**ので、どの段にいるかを票の §7（出典）に必ず書く。

| 段 | 手元にあるもの | やること |
|---|---|---|
| 2.1 | 業務を説明できる人がいる | 語りを並べ直す |
| 2.2 | 業界は決まっているが中身を知らない | **調査から入る（§2.2）** |
| 2.3 | 何もない | 想像。ただし歯止めが要る（§2.3） |

### 2.1 語りがある：時系列に並べ直す

もらった説明を、**誰が・何をする**の粒度で時系列に並べ、各行に印を付ける。

| 印 | 意味 | エージェントとの関係 |
|---|---|---|
| **変** | 非構造 → 構造の変換がある | ここが本体。LLM が要る唯一の場所であることが多い |
| **判** | 判断がある | ルールで書けるか、LLM が要るかを分ける |
| **参** | 台帳・マスタを引く | 検索。ここは決定論でよい |
| **待** | 人や外部を待つ | 図では見えないが、**速さの主張はここから出る** |
| **承** | 人が承認する | 権限の話。芯に効きやすい |

> Inquiry では「LINEで受ける（変）→ 物件・症状に分解（変）→ 優先度を判定（判）→
> 業者マスタを引く（参）→ 下書きを担当者が確認（承）→ 一次回答」と並んだ。

### 2.2 調査から入る：3つの入口

**一般的な市場調査をしても図にならない。** 「市場規模」「課題感」は票のどの項目にも
入らないからだ。**票の項目に直接対応する物を探しにいく。**

| 入口 | 探す物 | 票のどこが埋まるか |
|---|---|---|
| **A. 事故・トラブル** | 業界の事故報告、行政処分、判例、炎上事例 | **芯**（間違いのコストの非対称）。**最優先** |
| **B. 規程・帳票** | 法令、業界ガイドライン、社内規程、チェックリスト、既存の帳票 | **主体と権限**、**通らない経路**。決定論のルールがそのまま手に入る |
| **C. 困りごと** | 問い合わせログ、FAQ、クレーム、求人票の業務内容、業務マニュアル | **工程**、**具体シナリオ**の素材 |

#### A. 事故から入るのが一番よい

§3 のブレストで「間違いのコストが非対称」が最良の切り口だと書いた。
**事故事例はそれを直接探す方法**になる。

> ガス漏れの見落とし、期限徒過、与信の誤り、誤配薬。
> 「見逃すと重大／空振りは軽い」が業界の事故報告に必ず書いてある。

事故があるということは、**その業界には既に「防ぐための決まり」が文書で存在する**。
それが B につながる。

#### B. 規程は決定論ルールの金脈

エージェントの図で第3の主体（決定論のルール）を立てられるかは、
**「ルールが既に文章として存在するか」**で決まる。
規程・ガイドライン・チェックリストは、**そのままルールの箇条書きになる**。

> ClaimIntake のセーフティルール5本に相当するものが、
> どの業界にも規程として存在している。それを見つけると図が一気に立つ。

#### C. 困りごとは工程とシナリオの素材

FAQ とクレームは「非構造の入力」の実例そのもの。
**具体シナリオ（票 §6）の文面は、ここから採る**と作り物っぽさが消える。
求人票の「業務内容」も、工程を列挙してくれている点で使える。

### 2.3 想像で埋めるときの歯止め

調査もできないなら想像でよい。ただし放っておくと**きれいな道だけの図**になる。
歯止めを3つかける。

1. **図になるかの判定表（§3末）を先に当てる。** 主体が2つしかないなら、
   3つ目（ルール・台帳・記録）を作るところから設計する
2. **失敗を先に書く。** 「この工程で間違えると何が起きるか」を各工程に1行。
   書けない工程は、たぶん要らない工程
3. **通らない経路を意図的に2本作る。** 未実装のものと、条件が合わないもの。
   きれいな道しかない図は、商談で詰められたときに崩れる

そして**票 §7 に「構想」と明記し、どこまでが調査でどこからが想像かを分ける**。
混ぜると、あとで自分でも分からなくなる。

## 3. ブレスト：エージェントが効く場面の探し方

新しい題材を探すときの切り口。**上から順に当てていく**と出やすい。

1. **入口が非構造で、出口が構造**になっている仕事。
   雑な文章や音声が来て、決まった項目に落とす必要がある
2. **人が毎回同じ判断をしている**が、基準が言語化されていない。
   言語化するとルールになり、残りがLLMの仕事になる
3. **間違いのコストが非対称**。見逃しは重大で空振りは軽い、あるいはその逆。
   → **ここが一番よい。担保の設計が必要になり、それがそのまま図の主題になる**
4. **待ち時間が処理時間より長い**。実処理は数十秒なのに一次回答まで半日、など
5. **参照すべき台帳がある**。誰に振るか、どの規程が効くか
6. **すでに下書き→承認の形がある**。人が最終権限を持ったまま速くできる

### 図になるか、ならないか

| 図になる | 図になりにくい |
|---|---|
| 主体が3つ以上いて、**AIの出力を覆せるものが1つ以上ある** | 一直線の変換だけ（箇条書きで足りる） |
| 通らない経路や分岐がある | 分岐が無い |
| 記録が積まれる | 状態が1つしかない |
| 間違えたときの回復手段がある | 失敗したら終わり |

**主体が2つ（人とAI）だけなら、まだ掘りが足りない。**
たいてい3つ目（ルール、台帳、記録）が隠れている。

ただし**台帳や記録を数合わせに使わない**。参照されるだけで何も決めていないものは
主体ではない。物差しは「**AIがこう言っても、これが優先される**」と言えるかどうか。
言えないなら、その業務は図にしても山場が作れない。

## 4. 工程に割る

図にするには工程の列が要る。**時間で切らない。** 次のどちらかで切る。

- **主体が変わるところ**（AI → ルール → 人）
- **記録が増えるところ**（保存された、値が確定した）

割ったあと、次で検算する。

| 検算 | 目安 |
|---|---|
| 工程数 | **5〜7**。4未満は図にする意味が薄く、8以上は1枚に収まらない |
| 尺 | 1工程4秒。7工程で28秒。これが1枚ものの上限感 |
| 各工程に主体が1つ | 2つ以上あるなら割り方が粗い |
| 各工程に**作用**が1つ | 受け口 / 変換 / 推定 / 強制 / 参照 / 判断 / 出口 のどれか1つ。2つ混ざるなら割り方が粗い（[用語集](./agent-flow-glossary.md) §1.1） |
| 各工程で何かが増える | 何も増えない工程は消す |

> ClaimIntake は7工程（受付 / 文字起こし / AI判定 / ルール昇格 / 業務判断 / 人の確認 / 出口）、
> Inquiry は6工程。どちらも「主体が変わるところ」で切っている。

## 5. [2] への引き渡し票

**ここまでを次の7項目に埋める。埋まらない項目があるなら、まだ図にしない。**
図を描き始めてから調べ直すのが一番高くつく。

```markdown
## 1. 芯（商談で聞かれること）
一文。作り手が言いたいことではなく、相手が聞くこと。

## 2. 主体と権限
| 主体 | 決められること | 決められないこと |
|---|---|---|
主体が3つ未満なら、隠れている3つ目を探す。
**AIの出力を覆せる主体を1つ以上名指しする。**いないなら図の山場が作れない。

## 3. 工程
入口から出口まで5〜7個。主体が変わるところで切る。
各工程に「何が増えるか」を書く。

## 4. 記録されるもの
消えないもの、あとから追えるもの。
更新や削除が「無い」なら、無いと書く。

## 5. 通らない経路
未実装のもの、このシナリオでは条件が合わないもの。
図から消さずに残すので、ここに挙げておく。

## 6. 1件の具体シナリオ
値つきで。入力の実際の文面、AIの出力、確定値、所要時間。
※実測でない数字は「シナリオ値」と明記する。

## 7. 出典
実装のどのファイル / 誰のどの発言。
実装が無い場合は「構想」と明記する。
```

### 埋まっている例（ClaimIntake の抜粋）

- **芯**: AIが間違えたとき、どう担保するのか
- **主体**: AI（判定できる・降格できない）/ ルール（昇格を強制できる・降格できない）/
  人（降格できる・理由が要る）/ 記録（追記だけ・消せない）
- **通らない経路**: LINE webhook（未実装）、追加質問（P1では聞かない）
- **シナリオ**: 「キッチンの下から水が漏れています。ガスのようなにおいも少しします」
  → AI `P2` → `SAFETY_GAS_ODOR` で `P1` → 47秒で一次回答（シナリオ値）

この票がそのまま [2] の入力になり、
§6 のシナリオが [3] の「現場」の中身になる。

## 6. よくある外し方

- **機能を並べてしまう。** 「できること」の列挙は図にならない。
  権限と、できないことを書く
- **芯が作り手の言いたいこと**になっている。「AIが判定します」は芯ではない。
  相手が聞くのは「外したときどうするのか」
- **きれいな道だけ描く。** 通らない経路を消すと、図が実装より賢く見えてしまう。
  そのまま商談に出すと、詰められたときに崩れる
- **実測でない数字を実測のように書く。** 一度書くと図・現場・帯の3箇所に増殖する。
  最初から「シナリオ値」と決めて票に書いておく
