# [1] 題材の見つけ方

「どの業務にエージェントが効きそうか」を探し、**1枚のフロー図にできる形**まで持っていく手順。
図の描き方は [`agent-flow-diagram-patterns.md`](./agent-flow-diagram-patterns.md)（[2]）、
できた図を資料にするのは [`presentation-page-patterns.md`](./presentation-page-patterns.md)（[3]）。

この3本は鎖になっていて、**各段の出口が次の段の入口**になる。
この文書の出口は §5 の「引き渡し票」。

---

## 0. 出発点は2種類しかない

今回はこの2つを両方通した。入口が違うと調べ方が変わる。

| 入口 | 例 | 最初にやること |
|---|---|---|
| **実装がある** | ClaimIntake（PoCのコードがある） | コードを読んで、**実装が既に持っている主張**を探す（§1） |
| **話しかない** | Inquiry（業務の説明を文章でもらった） | 語りを時系列に並べ直す（§2） |

実装がある側が圧倒的に強い。**図に書けることが増えるのではなく、嘘を書けなくなる**から。
話しかない場合は「構想」と明示する。

---

## 1. 実装がある場合：コードから主張を掘る

探すのは機能ではなく、**設計者が何を守ろうとしたか**。次の4つを順に見る。

### (a) 型が分かれているところ

同じものに見えて別の型になっているなら、そこに主張がある。

> ClaimIntake では `Judgment`（AIの生出力・不変）と `ResolvedJudgment`（現在値）が
> 別の型だった。**「AIの出力を書き換えない」**という設計が型に出ていた。
> 図の主題はここで決まった。

### (b) 無い操作

CRUD のうち実装されていないものを探す。**無いことが主張**であることが多い。

> `inquiry_events` に update と delete が無い。追記のみ。
> ガードレールに「候補を削る」経路が無い。追加と制止だけ。

### (c) 非対称な権限

誰が何をできて、何をできないか。左右対称でないところが図の山場になる。

> 昇格はルールが強制できるが、降格は人しかできず理由が要る。
> **AIには降格の権限が無い。**

### (d) LLM を使っていないところ

AIの話なのに決定論で書かれている箇所は、たいてい「担保」のために意図的にそうなっている。

> セーフティルール5本は LLM を使わない決定論。だから図では
> AIでも人でもない第3の主体として立てた。

**(a)〜(d) で出たものを1文にまとめると、それが芯になる。**
ClaimIntake なら「AIが間違えたとき、どう担保するのか」。

---

## 2. 話しかない場合：語りを時系列に並べる

もらった説明を、**誰が・何をする**の粒度で時系列に並べ直す。
そのうえで各行に印を付ける。

| 印 | 意味 | エージェントとの関係 |
|---|---|---|
| **変** | 非構造 → 構造の変換がある | ここが本体。LLM が要る唯一の場所であることが多い |
| **判** | 判断がある | ルールで書けるか、LLM が要るかを分けて考える |
| **参** | 台帳・マスタを引く | 検索。ここは決定論でよい |
| **待** | 人や外部を待つ | 図では見えないが、**速さの主張はここから出る** |
| **承** | 人が承認する | 権限の話。芯に効きやすい |

> Inquiry では「LINEで受ける（変）→ 物件・症状に分解（変）→ 優先度を判定（判）→
> 業者マスタを引く（参）→ 下書きを担当者が確認（承）→ 一次回答」と並んだ。

## 3. ブレスト：エージェントが効く場面の探し方

新しい題材を探すときの切り口。**上から順に当てていく**と出やすい。

1. **入口が非構造で、出口が構造**になっている仕事。
   雑な文章や音声が来て、決まった項目に落とす必要がある
2. **人が毎回同じ判断をしている**が、基準が言語化されていない。
   言語化するとルールになり、残りがLLMの仕事になる
3. **間違いのコストが非対称**。見逃しは重大で空振りは軽い、あるいはその逆。
   → **ここが一番よい。担保の設計が必要になり、それがそのまま図の主題になる**
4. **待ち時間が処理時間より長い**。実処理は数十秒なのに一次回答まで半日、など
5. **参照すべき台帳がある**。誰に振るか、どの規程が効くか
6. **すでに下書き→承認の形がある**。人が最終権限を持ったまま速くできる

### 図になるか、ならないか

| 図になる | 図になりにくい |
|---|---|
| 主体が3つ以上いて、**権限が違う** | 一直線の変換だけ（箇条書きで足りる） |
| 通らない経路や分岐がある | 分岐が無い |
| 記録が積まれる | 状態が1つしかない |
| 間違えたときの回復手段がある | 失敗したら終わり |

**主体が2つ（人とAI）だけなら、まだ掘りが足りない。**
たいてい3つ目（ルール、台帳、記録）が隠れている。

## 4. 工程に割る

図にするには工程の列が要る。**時間で切らない。** 次のどちらかで切る。

- **主体が変わるところ**（AI → ルール → 人）
- **記録が増えるところ**（保存された、値が確定した）

割ったあと、次で検算する。

| 検算 | 目安 |
|---|---|
| 工程数 | **5〜7**。4未満は図にする意味が薄く、8以上は1枚に収まらない |
| 尺 | 1工程4秒。7工程で28秒。これが1枚ものの上限感 |
| 各工程に主体が1つ | 2つ以上あるなら割り方が粗い |
| 各工程で何かが増える | 何も増えない工程は消す |

> ClaimIntake は7工程（受付 / 文字起こし / AI判定 / ルール昇格 / 業務判断 / 人の確認 / 出口）、
> Inquiry は6工程。どちらも「主体が変わるところ」で切っている。

## 5. [2] への引き渡し票

**ここまでを次の7項目に埋める。埋まらない項目があるなら、まだ図にしない。**
図を描き始めてから調べ直すのが一番高くつく。

```markdown
## 1. 芯（商談で聞かれること）
一文。作り手が言いたいことではなく、相手が聞くこと。

## 2. 主体と権限
| 主体 | 決められること | 決められないこと |
|---|---|---|
主体が3つ未満なら、隠れている3つ目を探す。

## 3. 工程
入口から出口まで5〜7個。主体が変わるところで切る。
各工程に「何が増えるか」を書く。

## 4. 記録されるもの
消えないもの、あとから追えるもの。
更新や削除が「無い」なら、無いと書く。

## 5. 通らない経路
未実装のもの、このシナリオでは条件が合わないもの。
図から消さずに残すので、ここに挙げておく。

## 6. 1件の具体シナリオ
値つきで。入力の実際の文面、AIの出力、確定値、所要時間。
※実測でない数字は「シナリオ値」と明記する。

## 7. 出典
実装のどのファイル / 誰のどの発言。
実装が無い場合は「構想」と明記する。
```

### 埋まっている例（ClaimIntake の抜粋）

- **芯**: AIが間違えたとき、どう担保するのか
- **主体**: AI（判定できる・降格できない）/ ルール（昇格を強制できる・降格できない）/
  人（降格できる・理由が要る）/ 記録（追記だけ・消せない）
- **通らない経路**: LINE webhook（未実装）、追加質問（P1では聞かない）
- **シナリオ**: 「キッチンの下から水が漏れています。ガスのようなにおいも少しします」
  → AI `P2` → `SAFETY_GAS_ODOR` で `P1` → 47秒で一次回答（シナリオ値）

この票がそのまま [2] の入力になり、
§6 のシナリオが [3] の「現場」の中身になる。

## 6. よくある外し方

- **機能を並べてしまう。** 「できること」の列挙は図にならない。
  権限と、できないことを書く
- **芯が作り手の言いたいこと**になっている。「AIが判定します」は芯ではない。
  相手が聞くのは「外したときどうするのか」
- **きれいな道だけ描く。** 通らない経路を消すと、図が実装より賢く見えてしまう。
  そのまま商談に出すと、詰められたときに崩れる
- **実測でない数字を実測のように書く。** 一度書くと図・現場・帯の3箇所に増殖する。
  最初から「シナリオ値」と決めて票に書いておく
