前段の調査は [`adoption-candidates.md`](./adoption-candidates.md) の「Transit調査結果」。
図の作法は [`agent-flow-diagram-patterns.md`](./agent-flow-diagram-patterns.md)、

## 1. 決まったこと

調査で「Transit は `variant` とは別の概念」と分かった。
そのうえで、**既存 Transit の役割別3帯は追わない。主体別3帯の新しいレイアウトを作る。**

つまり `Diagram-Transit` の再現ではない。**別物を作る。**
`Diagram-Transit` は Inquiry の試作としてそのまま残す。

---

## 2. 調査で分かっている前提

### 帯の割り当てに使える情報は揃っている

調査で「`tone` だけでは外部の人と内部の工程を分けられない」と出たが、
**位置を併せれば分けられる。**

| 題材 | `tone: "input"` のノード | 位置 |
|---|---|---|
| ClaimIntake | `resident` / `intake` / `stt` | 外 / 中 / 中 |
| Restoration | `tenant` / `walkthrough` / `photos` / `vendor` | 外 / 中 / 中 / 中 |
| Proposal | `lead` / `intake` | 外 / 中 |

**外部の登場人物は、枠の左外に置かれている**（`OUTSIDE_CX = 150`、枠は `x = 320` から）。
3題材とも同じ。だから

```
外部の登場人物 = tone が "input" かつ、水平方向に枠の外
```

で判定できる。**新しい注釈は要らない。**

> 判定を水平方向に限るのが要点。担当者と出口は枠の**下**にあり、
> 記録チップは枠の**右**にある。上下や右で判定すると巻き込む。

### 揃っていない情報がひとつある

**`EdgeDef` は `points`（経由点）を持つが、`from` / `to` を持たない。**
配置を変えると経由点は使えなくなるので、**線の端点はここで足す必要がある。**

ID から取れると思いたくなるが取れない。実例:

- `staff-resolved` の実際の接続先は `recResolved`
- `special-clause` は `classify` → `staff`（IDに端点が入っていない）

**足すのは「各エッジの端点2つ」だけ。** 座標表は作らない。

---

## 3. 帯の割り当て（案・変えてよい）

6つの `tone` を3帯に落とす。**下は提案で、実装しながら変えてよい。**

| 帯 | 入るもの | 見出しの例 |
|---|---|---|
| **1** | `input` かつ枠の外 / 出口のノード | 外から入る・外へ出る |
| **2** | `input` かつ枠の中 / `ai` | エージェントが処理する |
| **3** | `rule` / `human` | ルールと人が決める |

- **記録チップ（`record: true`）は帯に入れない。** いまと同じく独立した列にする。
  「流れ」ではなく「積み重なり」なので、帯に混ぜると流れに見える
- **`planned`（通らない経路）は、隣り合うノードの帯に置く。** 消さずに破線で残す
- **`rule` と `human` を同じ帯にしたのは、どちらも「AIでないものが決める」から。**
  この図の芯（AI・ルール・人の権限の非対称）を帯で見せたいなら、
  2と3の対比がそれになる。**別の切り方のほうが良ければ変えてよい**

## 4. やってほしいこと

### 手1：1題材で作る

**Restoration か Proposal で1枚作る。** どちらも `constants.ts` が既に `FlowSpec` を
組んでいるので扱いやすい。両方はやらなくてよい。

- 帯の割り当ては §3 から導く（手で座標表を書かない）
- 帯の中の並び順は、既存の `cx` の順を使ってよい
- 線は §2 で足した端点から引く。**直角ルーティングでよい**
  （`shared/orthogonalRouting.ts` の `roundedPath`）

### 手2：4題材に広がるかを見る

1枚できたら、**残り3題材で同じコードが動くか**だけ確かめる。
崩れるなら、何が足りないかを書く。**全部をきれいに仕上げる必要はない。**

---

## 5. 終わってよい条件

- 1題材で、**全ノードと全エッジが出ている**（数を数えて合っていればよい）
- **通らない経路が破線で残っている**
- **決定論のルールが白**
- 残り3題材で動くか動かないかが言える

**見た目の作り込みは要らない。** 線が少し重なっていてもよい。
判定は「導けているか」であって「きれいか」ではない。

---

## 6. 守ること

### 既存の出力を変えない

**既存のコンポジションに手を入れるときは、既定値で従来どおりになるフラグを足す。**
`hidePanel` / `inactiveDashed` / `frameOverride` / `inactiveDashed` がその形。

`EdgeDef` に `from` / `to` を足すのは**任意フィールド**にすれば既存は壊れない。

変えていないことは**同じフレームのPNGを `cmp` でバイト比較**して示す。

```sh
pnpm exec remotion still <Id> before.png --frame=420 --gl=swangle
# ...変更...
pnpm exec remotion still <Id> after.png --frame=420 --gl=swangle
cmp before.png after.png
```

レンダーの前後でソースの `md5` も取る。

### 図の作法

- **座標を2箇所に書かない。** これがこの依頼の主題
- **主体に色を割り当てる**（工程ではない）。決定論のルールは白
- **通らない経路を消さない**
- **上書きのアニメーションを作らない**

### 置き場と名前

`AgentFlow > DesignStudies > AgentDiagram`、ID は `Diagram-<名前>`。
**`Diagram-Transit` とは別物なので、別の名前にする**（`Diagram-Bands` など）。

登録したら一覧を作り直す。

```sh
pnpm gallery:agent-flow   # 忘れると pnpm test:gallery が落ちる
pnpm test                 # 28件
```
