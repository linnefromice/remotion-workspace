# 調査を外部のLLMに頼むときの依頼書

[`agent-flow-discovery.md`](./agent-flow-discovery.md)（[1]）§2.2 の調査を、
Web検索ができるLLMに任せるための貼り付け用テキスト。

## 使い方

3本を順に使う。**2本目までで止めない。3本目（粗探し）が一番効く。**

```
P1 領域を洗い出す      → 候補が10件ほど、図になりやすい順に並ぶ
P2 1つ選んで深掘る     → [1]→[2] の引き渡し票が埋まる
P3 埋まった票を疑う    → 捏造と「きれいすぎ」が落ちる
```

## なぜ普通の調査依頼ではだめか

「〇〇業界の課題を調べて」と頼むと、市場規模と課題感が返ってくる。
**それは引き渡し票のどの項目にも入らない。**

票が要求するのは「主体と権限」「通らない経路」「値つきの具体シナリオ」。
だから**依頼文の側に票の形を先に書いて、それを埋めさせる**。
以下の依頼書はすべてその作りになっている。

---

## P1. 領域を洗い出す

<!-- ここから貼り付け -->
```
AIエージェントの業務フロー図を作るための題材を探しています。
以下の条件に合う業務を10件挙げ、条件を満たす度合いが高い順に並べてください。

# 対象
<業界・職種・企業規模などをここに書く。例: 日本の不動産賃貸管理会社（従業員50〜300名）>

# 良い題材の条件（満たすほど上位）
1. 判断を間違えたときのコストが非対称である
   （見逃すと重大／空振りは軽い、またはその逆）
2. 入口が非構造（文章・音声・画像）で、出口が構造（区分・優先度・担当）である
3. 判断に関わる主体が3つ以上いる
   （例: 現場の人／AI／決まったルール／台帳／記録。人とAIの2つだけは不可）
4. その業界に、守るべきルールが「文書として既に存在する」
   （法令、業界ガイドライン、社内規程、チェックリストなど）
5. 待ち時間が実処理時間より明らかに長い
6. 人が最終承認する形が既にある

# 出力（1件ごとにこの形で）
- 業務名:
- なぜ非対称か: 見逃したとき何が起きるか / 空振りのコスト
- 入口と出口: 何が来て、何に変換されるか
- 主体（3つ以上）: それぞれ何を決められるか
- 既にある文書のルール: 名称と、あれば出典URL
- 条件の充足: 1〜6のうち満たすもの（番号）
- 出典: URL。無い場合は【推測】と明記

# 守ること
- 数字を出すときは必ず出典URLを付ける。無いなら書かない
- 一般論（「DXが進んでいない」「人手不足」）は書かない。業務単位で書く
- 主体が人とAIの2つしか挙げられない業務は、候補から外す
```

## P2. 1つ選んで深掘る

P1 の結果から1つ選び、票を埋めさせる。**出力形式をそのまま指定する**のが要。

<!-- ここから貼り付け -->
```
以下の業務について、フロー図を作るための情報を調べてください。

# 対象業務
<P1 の結果から1件を貼る>

# 特に探してほしいもの（優先順）
1. 事故・トラブルの実例
   行政処分、事故報告、判例、報道。「見逃して何が起きたか」の具体例
2. 守るべきルールの文書
   法令の条番号、業界ガイドライン、チェックリスト。
   条件つきで判断が決まるもの（「〇〇の場合は必ず△△する」）を優先
3. 実際の入力の文面
   FAQ、問い合わせ例、クレーム事例。素人が書いた生の文章が望ましい
4. 誰が何を承認するか
   権限規程、業務分掌。「誰なら覆せるか」「覆すとき何が要るか」

# 出力（この見出しのまま）
## 1. 芯
商談で相手が聞いてくる問いを一文で。作り手が言いたいことではない。

## 2. 主体と権限
| 主体 | 決められること | 決められないこと |
主体は3つ以上。「決められないこと」が空の主体は挙げない。

## 3. 工程
入口から出口まで5〜7個。時間ではなく「主体が変わるところ」で切る。
各工程に「そこで何が増えるか（保存される・確定する）」を書く。

## 4. 記録されるもの
あとから追えるもの。更新や削除ができない決まりがあるなら、それも書く。

## 5. 通らない経路
実務では起こりうるが、この筋では通らないもの。最低2本。
（条件が合わないもの、まだ手が付いていないもの）

## 6. 1件の具体シナリオ
値つきで。実際の入力文（1〜2文）、AIが出すであろう判定値、
ルールが効いた後の確定値、発火するルールの名称、所要時間。
※実測でない数字はすべて「シナリオ値」と書く

## 7. 出典
項目ごとにURL。推測で埋めた箇所は【推測】と明記。

# 守ること
- 出典のない数字を書かない。必要なら「シナリオ値」と断る
- 「AIが判定します」で終わらせない。外したときに何が効くかまで書く
- きれいな道だけ書かない。5 が埋まらないなら、まだ調べ足りない
```

## P3. 埋まった票を疑う

**ここが一番効く。** 別のセッション（できれば別のモデル）に、
敵対的に読ませる。素直に深掘りすると、LLM は「きれいな業務」を書きがちなので、
それを落とす工程を必ず挟む。

<!-- ここから貼り付け -->
```
以下は、ある業務についての調査結果です。これから図にするので、
**そのまま信じずに粗を探してください。** 良い点は書かなくて結構です。

<P2 の出力を貼る>

# 見てほしい観点
1. 出典が無いのに断定している箇所はどこか
2. 数字のうち、実測なのかシナリオ値なのか曖昧なものはどれか
3. 「主体」に挙がっているが、実は何も決めていないものはあるか
4. 「決められないこと」が書かれていない主体はあるか
   （権限の非対称が無いなら、図にする価値が薄い）
5. 工程のうち、何も増えていない（消してよい）ものはどれか
6. 通らない経路が形式的で、実務では起きなさそうなものはどれか
7. この業界を知る人が読んだとき、いちばん最初に「それは違う」と言いそうな箇所はどこか

# 出力
- 落とすべき記述: 箇条書きで、理由つき
- 確認が必要な箇所: 誰に何を聞けば確かめられるか
- この題材は図にする価値があるか: あり／なし と、その理由を3行で
```

## 受け取ったあとにやること

LLM の出力をそのまま票にしない。**必ず自分で3つ確認する。**

| 確認 | 落ちやすいもの |
|---|---|
| 主体が本当に3つ以上か | 「台帳」「記録」を主体として水増ししているだけのことがある。**何かを決めているか**で判定する |
| 「決められないこと」が埋まっているか | ここが空だと権限の非対称が無い。図の山場が作れない |
| 具体シナリオの文面が生きているか | LLM が書く問い合わせ文は整いすぎる。**FAQ やクレームの実文に寄せて書き直す** |

そのうえで、票 §7（出典）に**どこまでが調査で、どこからが自分の想像か**を線引きして書く。
これをやらないと、[2] で図にしたとき自分でも根拠を思い出せなくなる。

---

## 注意

- ここで集めるのは**外部の公開情報**。特定企業の非公開の業務や、
  顧客から預かった情報を検索サービスに投げない
- 出てきた事故事例を図に使うときは、**企業名を出さない**。
  「〇〇社の事故」ではなく「ガス漏れの見落とし」の水準にする
- 規程や条文を引くときは、**改正で変わる**。票 §7 に参照した日付を書く
