# デモ用の見せ物 索引

**何があるかの正本は `pnpm gallery:agent-flow` が作る一覧**（§デザインリスト）。
この文書は、そこに並ぶものが**どういう性格か**を書く。

`AgentFlow > ClaimIntake` に並んでいる「プレゼン用の見せ物」が何であるか、
どれを商談のどこで使うかの索引。

どれも同じ1件を扱う。**入居者が「キッチンの下から水が漏れています。
ガスのようなにおいも少しします」と通報し、AIはP2（翌営業日）と判定するが、
安全ルール `SAFETY_GAS_ODOR` が発火してP1（即時）へ引き上げる**という筋。
尺は全部 1920×1080 / 30fps / 840フレーム（28秒 = 120フレーム×7工程）。

つくり方の手順は [`presentation-production-playbook.md`](./presentation-production-playbook.md)
（各段の詳細は [[1] 題材](./agent-flow-discovery.md) → [[2] 図](./agent-flow-diagram-patterns.md)
→ [[3] 1枚](./presentation-page-patterns.md)）、
経緯は [`presentation-site.md`](./presentation-site.md)、
引き継ぎ用の一枚は [`presentation-site-brief.md`](./presentation-site-brief.md)。

## 1. 2つの系統

同じ問い（AIが間違えたらどうするのか）に、性格の違う2つの答え方がある。

| | SideBySide 系 | DecisionStory |
|---|---|---|
| 画面の主役 | フロー図＋そのとき出ている画面 | 文字。図は無い |
| 見る人の視線 | 左右に往復する | 上から下へ一方向 |
| 強み | **仕組みと現物が同時に見える** | **遠くからでも読める。1文が刺さる** |
| 弱み | 情報量が多く、視線が散る | 全体の経路が分からない |
| 向く場面 | 座って一緒に見るとき | 展示会で立ったまま見るとき |

**商談では DecisionStory で掴んで、SideBySide で構造を見せる**のが素直な順番。
どちらかを選ぶより、並べて使うほうが噛み合う。

## 2. SideBySide 系

フロー動画を `transform: scale()` で 0.59 倍にして左に埋め、
右に**そのステップで実際に出ている画面**を並べる。

右側は7工程ぶん用意してある。

| 工程 | 右に出るもの |
|---|---|
| 受付 | 入居者のスマホ（LINEのトーク画面） |
| 文字起こし | 音声の波形と、起こされたテキスト |
| AI判定 | **AIの生出力** `{"urgency":"P2","confidence":"medium"}` |
| ルール昇格 | 発火した `SAFETY_GAS_ODOR` と、書き換わらず並ぶ2つの値 |
| 業務判断 | NextAction候補（ガードレールが足したものに印） |
| 人の確認 | 担当者の管理画面（P1バッジ・「降格には理由が必要」） |
| 出口 | CSVの1行（`urgency_ai` と `fired_rule_ids` が並ぶ） |

狙いは1つ。**「AIがP2と言った」は抽象だが、JSONに `"P2"` と書いてあるのを
見せると現実になる。**

### 5つの版

中身は同じコンポーネントで、`zod` スキーマの4つのフラグが違うだけ。
**Studio の props パネルから、ここに無い組み合わせも試せる。**

| コンポジション | フラグ | 何が違うか |
|---|---|---|
| `ClaimIntake-SideBySide` | なし | 素の形。左右に並べただけ |
| `ClaimIntake-SideBySide-Map` | `mapOnly` | 左のフロー図から判定パネルを外す |
| `ClaimIntake-SideBySide-Counterfactual` | `counterfactual` | 下段に、ルールの有無で結末が変わることを置く |
| `ClaimIntake-SideBySide-Full` | `mapOnly` `counterfactual` `clock` | 上の2つ＋経過時計。**いまの推奨** |
| `ClaimIntake-SideBySide-Timeline` | `mapOnly` `timeline` | 下段が、イベントが左から積まれる時間軸 |

#### `-Map` — 左を地図に徹させる

素の形だと、**左のフロー図が持つ「判定の非対称」パネルと、右のステップ4が
同じ値（AI P2 / ルール P1）を2回言う**。`mapOnly` はその重複を消す。

- 得: 主張が1箇所になる。右が唯一の声になる
- 損: フロー図の左下が空く。地図としては困らないが、枠内が少し寂しい

#### `-Counterfactual` — 語れないことを語る

フロー図は仕組みを語れるが、**失敗したときの損失を語れない**。下段の帯で補う。

| | 結末 |
|---|---|
| ルールが無い場合 | AIのP2のまま → 翌営業日に手配 → ガスのにおいは誰も見ない |
| ルールがある場合 | P1へ昇格 → 即時架電・当日手配 → 47秒で一次回答 |

工程4（ルール昇格）から「ある場合」だけが点灯する。それまではどちらも中立。
**「AIが間違えたら？」への直接の答えなので、5つの中では一番刺さりやすい。**

#### `-Timeline` — 追記のみと、速さを同時に

経過時間と `inquiry_events` の追記を別々に作ろうとして、
**1920×1080 に左右2カラムを置くと縦に積める余地が下に1帯ぶんしかない**と判明した。
横軸を時間にしてイベントを左から積むと、同じ場所で両方言える。

- 一度出た点が最後まで残る → **追記のみ（消えない）**が見える
- 目盛りの詰まり方 → **0〜22秒に6件が固まり、そこから47秒まで空く**。
  待ち時間がどこにあるかが図になった

`counterfactual` と場所を取り合うので**排他**。両方見せたいなら、
キャンバスを変えるか、時間で切り替えるか、サイトにするしかない。

#### `-Full` — いまの推奨

`-Map` で左を黙らせ、`-Counterfactual` を足し、ヘッダ右に経過時計を出したもの。
順番として、左の重複を消してから下段を足すのが正しい。

### 触るときの注意

**同じ数字を3箇所で言ってしまいがち。** 「47秒」が時計・現場（出口）・反実仮想で
重なったので、`hideElapsed` で抑えている。要素を足すたびに
「既にどこかで言っていないか」を確認すること。

### ファイルの置き場

```
src/ClaimIntakeSideBySide/
  index.tsx                   ページのレイアウト。公開窓口も兼ねる
  constants.ts                寸法（FLOW / STAGE）・スキーマ・プリセット
  scenario.ts                 この1件の事実（受付番号・AIの値・ルールID・経過秒）
  parts/primitives.tsx        Caption / CodeBlock / Phone / Badge / Row など小部品
  scenes/index.tsx            工程ごとの「現場」7枚と、それを並べた SCENES
  panels/Counterfactual.tsx   下段の帯（反実仮想）
  panels/EventTimeline.tsx    下段の帯（追記タイムライン）と経過時計
```

寸法は `constants.ts`、シナリオの値は `scenario.ts` にしか書かない。
`P2` `P1` `SAFETY_GAS_ODOR` `47` は現場・下段の帯・タイムラインの3箇所から
参照されるので、直書きすると必ずずれる。
フロー図は `AgentFlowClaimIntakeIcons` をそのまま縮小して埋めていて、
中身は `useCurrentFrame()` から状態が決まるので**同期のコードは無い**。

## 3. `ClaimIntake-DecisionStory`

図をやめて、**1件の判断記録が積まれていく様子**を文字で見せる版。
工程ごとに大きな見出しが変わる（「安全ルールが、即時対応を要求。」など）。

- 上段左: 通報文そのもの。工程2で「ガスのようなにおい」に下線が引かれる
- 上段右: **AIの原判定(P2)と安全ルールの結論(P1)を別々の欄に並べる**。
  どちらも大きな数字で、片方が消えないことが一目で分かる
- 中段: 工程ごとに入れ替わる帯（問い → 比較用の仮定 → ガードレール → 権限の非対称 → 記録）
- 下段: 7工程の記録。通った工程は実線、これからは破線

図が無いぶん**文字が大きく、遠くからでも読める**。
そのかわり、どこからどこへ流れているのかは分からないので、
全体像は SideBySide 系に任せる前提になっている。

`showComparison` を false にすると、工程4の比較帯が原値保存の説明に替わる。

### フロー図を添えた版

DecisionStory の弱点（全体の経路が分からない）を、既存のフロー図で埋めたもの。

| コンポジション | 置き方 |
|---|---|
| `ClaimIntake-DecisionStory-Side` | 横に並べる。**こちらを推奨** |
| `ClaimIntake-DecisionStory-Stacked` | 縦に積む |

どちらも 1920×1080 を前提に作られた2枚を1枚に入れるので、
**両方が読める大きさには収まらない**。主役は DecisionStory のままにして、
フロー図は「いまどこの話か」だけを示す地図まで小さくしてある。
判定の値は DecisionStory が言うので、地図側の判定パネルは外している。

縦積みは左右が大きく余る。横並びのほうが締まる。

### ファイルの置き場

```
src/ClaimIntakeDecisionStory/
  index.tsx     本体。工程ごとの文言は STEPS に1つにまとめてある
  WithMap.tsx   フロー図を地図として添える版（横並び / 縦積み）
```

## 4. 言い回しの約束

どの版でも守っているもの。題材の実装に無いことを図が主張しないための線引き。

- **47秒はシナリオ値**。実測でも性能保証でもない。DecisionStory は画面下に明記している
- **AIの値を上書きするアニメーションを作らない**。実装が「書き換えない」設計なので、
  上書きの演出は嘘になる。2つの値を並べて片方に印を付ける形にしている
- **決定論のルールに色相を与えない**。AIでも人でもない第3の主体は白で立てる
- **通らない経路を消さない**。未実装の経路も、条件が合わず今回通らない工程も破線で残す
- **架空の降格実績を作らない**。降格は人だけ・理由必須という権限の説明にとどめる

---

## 5. 残っていること

1. **触って試せる要素**。定型文を数個から選ぶと発火するルールが変わる程度のもの。
   「説明された」が「試した」に変わるはずだが、**動画では作れない**
2. **降格のシナリオ**。判定の非対称の片側（ルールによる昇格）しか描けていない。
   AIがP1と言い、人が理由を書いて下げる側を見せると、主張が両側そろう
3. **元の図のラベル重なり**。`ClaimIntake-IconsV2` の LINE ノードで
   「Webhook / 外部チャネル」の折り返しが下のタグに被っている

## デザインリスト（2026-09-18）

**正本は自動生成の一覧。** `pnpm gallery:agent-flow` が `out/agent-flow-gallery/index.html` を作る。

```bash
pnpm gallery:agent-flow                # 各動画の中間フレームで全AgentFlowを撮る
open out/agent-flow-gallery/index.html
```

### 決めたこと

| | 決定 | 理由 |
|---|---|---|
| **正本** | **自動生成の一覧** | `src/Root.tsx` を AST で読むので登録漏れが起きない。手で書いた索引と二重に持つと必ず片方が古くなる |
| **並べる軸** | **題材** | Studio のフォルダ階層と一致する。ID から置き場も引ける |
| **試行と成果物の線引き** | **いまはしない** | 区別せずに並べ、あとで整理を検討する |

### 更新の決まり

**`AgentFlow` にコンポジションを足したら、同じ変更のなかで一覧を作り直す。**

```bash
pnpm gallery:agent-flow
```

- 一覧は `src/Root.tsx` を読むので、**登録しただけでは一覧に出ない**。
  作り直して初めて載る。登録だけで止めると、正本が実態とずれる
- 図の見た目を変えたときも作り直す。一覧の静止画が古いままになる
- 出力は `out/` 配下で git 対象外。**リポジトリには入らないので、
  手元で作り直す以外に最新にする方法がない**
- 全件成功したときだけ `index.html` が差し替わる。途中で失敗しても前回の一覧は壊れない

**作り直し忘れはテストで落ちる。**

```bash
pnpm test:gallery
```

公開中の一覧と `src/Root.tsx` の登録を突き合わせ、
載っていない図・消えた図が残っている場合・題材が変わった場合・画像が消えた場合に失敗する。
一覧をまだ一度も作っていない環境では skip する（古い一覧に騙される危険が無いため）。

**検出できないもの**: 図の**見た目だけ**を変えて作り直していない場合。
登録が変わらないので分からない。ここは引き続き人が気をつける。

同じことを [`CLAUDE.md`](../CLAUDE.md) の «Adding a New Composition» と
[[2] の検算](./agent-flow-diagram-patterns.md#8-できたかどうかの検算) にも書いてある。

### この文書の役割

**一覧に「何があるか」は任せ、この文書は「どれがどういう性格か」を書く。**
自動生成の一覧は各案の見た目と寸法しか持てないので、
用途・強み・弱み・言い回しの約束は人が書くしかない。

いまは ClaimIntake が中心の記述になっている。Inquiry の DesignStudies 8案は
[`inquiry-design-studies.md`](./inquiry-design-studies.md)、
Restoration / Proposal は各設計メモにある。**一覧が正本になったので、
この文書からそちらへ辿れれば足りる**（重複して書き写さない）。
