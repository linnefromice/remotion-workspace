# [2] ノード図の作り方

[1]（[`agent-flow-discovery.md`](./agent-flow-discovery.md)）の引き渡し票を受け取って、
1枚のフロー図に落とすまで。できた図を資料にするのは
[`presentation-page-patterns.md`](./presentation-page-patterns.md)（[3]）。

用語の対応表は [`agent-flow-glossary.md`](./agent-flow-glossary.md)。
**指示を書くときはそちらの言葉を使う。**

実際に作った2枚（ClaimIntake / Inquiry）から、繰り返し使える形を抜き出したもの。
個別の設計は [`agent-flow-claim-intake.md`](./agent-flow-claim-intake.md) と
[`agent-flow-inquiry.md`](./agent-flow-inquiry.md) にある。

---

## 0. 入力の確認

引き渡し票の7項目が埋まっていること。特にこの3つが無いと手が止まる。

- **主体と権限**（§2）→ 色の割り当てが決まらない
- **工程**（§3）→ 列の数と尺が決まらない
- **通らない経路**（§5）→ あとから足すとレイアウトが崩れる

---

## 1. 骨格のパターン

> ノードを置く前に、**各ノードの作用**（受け口 / 変換 / 推定 / 強制 / 参照 / 判断 / 出口 / 記録 / 残置）と
> **強制の向き**（昇格 / 減額 / 除外 / 追加 / 制止）を決めておく。
> [用語集](./agent-flow-glossary.md) §1。色（トーン）はそのあと自動的に決まる。


2枚とも同じ骨格に落ち着いた。**まずこれを当ててみて、合わなければ崩す。**

```
┌─ 外側 ─┬──────── ランタイム枠 ────────┐  ┌ 記録層 ┐
│ 登場人物 │  ROW_1  主系列 →→→→→→→→→   │  │ ▭ 会話  │
│  ▢ 入居者│                              │  │ ▭ 判定  │
│  ▢ LINE  │  ROW_2  分岐・2段目           │  │ ▭ 現在値│
└─────────┴──────────────────────────────┘  └────────┘
              ▢ 人          ▢ 出口
```

- **外側**: システムの外にいる人・チャネル。枠の中に入れない
- **ランタイム枠**: 実装の責任範囲。枠線を引いて「ここがアプリ」と示す
- **記録層**: 右端に縦に並べる。**フローの箱と違う見た目にする**（小さい・アイコン無し）。
  流れではなく積み重なりなので、同じ形にすると読み違える
- **枠の外下**: 人の判断と出口。ランタイムの外で起きることを下に出す

### 行の意味づけ

| 行 | 置くもの |
|---|---|
| ROW_1 | 主系列。入口から出口まで一直線に読める並び |
| ROW_2 | 分岐、2段目の判定、通らない経路 |
| ROW_3 | （Inquiry のみ）改善サイクルなど、時間軸が違うもの |

**主系列が一直線に読めることを最優先**にする。ROW_1 が折れると図が急に難しくなる。

## 2. 座標の作り方

**座標を2箇所に書かない。** これが最も効いた作法。

```ts
const COL_A = FRAME_X + FRAME_MARGIN + NODE_W / 2;
const COL_B = COL_A + NODE_W + COL_GAP;
const COL_C = COL_B + NODE_W + COL_GAP;
const ROW_1 = FRAME_Y + FRAME_MARGIN + NODE_H / 2;
const ROW_2 = ROW_1 + NODE_H + ROW_GAP;
```

ノードの位置も、エッジの経由点も、**すべてこの定数から導く**。

```ts
// エッジは「どのノードのどの辺から」で書く。数値を直接書かない
points: [[right("intake"), cy("intake")], [left("stt"), cy("stt")]]
```

これを最初からやった図は、**ノードサイズを何度変えてもエッジ側を触らずに済んだ**。
逆に、手描きのパス文字列（`'M380 306 H575'`）を持っていた図は、
ノードを動かすたびに線がズレるバグが出た。

### 実測値（参考）

| | ClaimIntake | Inquiry |
|---|---|---|
| ノード | 208 × 116 | 208 × 116 |
| 列間 / 行間 | 75 / 80 | 同等 |
| 枠 | 4列 × 2行 + 余白36 | 3列 × 3行 |
| 記録チップ | 208 × 62 | なし |

例外ノードはサイズを変えてよい（Inquiry の承認ゲートだけ 168×92 の破線）。
**例外は小さくする。** 大きくすると主系列より目立つ。

## 3. 線のパターン

### 直角ルーティング

斜めのベジェはノードの枠や文字を横切りやすい。**経由点の配列を持たせ、角丸の折れ線で描く。**

```ts
points: [
  [cx("safety"), bottom("safety")],
  [cx("safety"), WORK_TURN_Y],   // いったん下りて
  [cx("work"),   WORK_TURN_Y],   // 横に振って
  [cx("work"),   top("work")],   // 入る
]
```

折り返しの高さ（`WORK_TURN_Y`）は名前付き定数にする。複数の線で共有すると揃う。
角の丸めは 18px。図全体で1つに統一する。

### 線種の使い分け

| 線種 | 意味 |
|---|---|
| 実線 | 通る経路 |
| 破線 | **未実装 / このシナリオでは条件が合わない / 参照** |
| 灰色（系統色なし） | 参照であって流れではない（業者マスタを引く、など） |

**通らない経路を消さない。** 実装にあるものを図から消すと、図が実装より賢く見える。
商談で詰められたときに崩れる。

### 説明映像でも全経路を残す

「いま何が起きているか」を拡大して見せる場合も、同じ画面内で全経路を確認できるようにする。
別のコンポジションを一緒に使うだけでは、単体で見たときの経路の欠落を解消できない。

- 全体図を主役にする案は、非アクティブな接続を薄い破線で残す。
- 1つの受け渡しを拡大する案は、全経路を示す小さな地図を常設する。
- 「薄い破線＝その他の経路」「強調線＋動く点＝現在」と凡例で区別する。
  現在の経路が参照・非同期・任意工程なら、強調線も破線のままとする。
- 全体図と拡大表示の現在の経路を同期する。表示用の案件カードなどを、実際の処理ノードとして図に加えない。

Inquiry DesignStudies 全8案に適用済み。以前の「その瞬間の1本だけを表示する」例外は撤回した。

### 矢印

SVG の `<marker>` は色を継承しない。**色ごとに marker を用意して id で引く**。
接頭辞を図ごとに変えないと、同じページに2枚置いたとき衝突する。

## 4. 色の割り当て

**主体に色を割り当てる。工程ではない。** 工程に色を振ると、
同じ主体が違う色で出てきて読み手が混乱する。

| 主体 | 色 | 理由 |
|---|---|---|
| 入力 | シアン | 外から来るもの |
| AIの推論 | 紫 | 確率的なもの |
| **決定論のルール** | **白（無彩色）** | AIでも人でもない第3の主体。**新しい色相を発明せず、最強コントラストで立てる** |
| 人の判断 | オレンジ | 介在 |
| 記録 | 緑 | 積まれるもの |

ルールを白にするのは ClaimIntake の実装自身の判断を借りたもので、
**「ルールはAIの一種ではない」を色で言っている**。
主体が3つ以上いる図では、この「無彩色の第3極」が効く。

## 5. 時間の作り方

- **1工程 = 120フレーム（4秒）**。7工程で28秒。これが1枚ものの上限感
- 工程ごとに、その工程のエッジだけが光る
- 同じ工程に2本の線があるなら `delay` でずらす（45フレームなど）。同時に光ると読めない
- **上書きのアニメーションを作らない。** AIの値をルールが書き換える演出は、
  実装が「書き換えない」設計である以上、嘘になる。
  **2つの値を並べて片方に印を付ける**形にする

### 状態はフレームの純関数にする

```ts
const step = Math.floor(frame / STEP_LEN);
```

`useCurrentFrame()` 以外から状態を作らない。これを守ると、
**同じフレームは何度描いても同じ絵**になり、途中のフレームだけ書き出して確認できる。
[3] で図を縮小して埋め込むときも、同期のコードが要らなくなる。

## 6. 4つの版を規定で作る

**図は1枚では終わらせない。同じ構造のまま、ノードの描き方だけ変えた4版を必ず作る。**
用途ごとに要る版が違い、あとから足すより最初に揃えるほうが安い。

| 版 | ID の接尾辞 | 見た目 | 向く場面 |
|---|---|---|---|
| **Cards** | `-Cards` | 箱に説明文つき | **単体で読ませる**とき。設計資料。文字が多い |
| **LogoSeal** | `-LogoSeal` | 円形の中にアイコン、下にラベル | 一覧性が要るとき。**スライドの1枚**に向く |
| **IconsV2** | `-IconsV2` | LogoSeal ＋ 実サービスのロゴ | **「本物と繋がる」を言いたい**とき（LINE、Gmail） |
| **ActionRow** | `-ActionRow` | 箱に短い動作を1行 | **縮小して埋め込む**とき。文字が少なく潰れにくい |

構造・タイムライン・山場のパネルは**共有し、差分は描き方だけに閉じる**。
[3] でどれを使うかを選べるようになる。

### 実装の型

`FlowSpec`（データ）と描画を分け、版は props で切り替える。

```tsx
export const Flow: React.FC = () => <FlowDiagram spec={SPEC} />;
export const FlowLogoSeal: React.FC = () => <FlowDiagram spec={SPEC} variant="logoSeal" />;
export const FlowActionRow: React.FC = () => <FlowDiagram spec={SPEC} variant="actionRow" />;
export const FlowIconsV2: React.FC = () => <FlowDiagram spec={SPEC} variant="logoSeal" brandIcons />;
```

`FlowSpec` に `brands` を持たせ、実ロゴを出すノードだけ指定する。
ロゴの持ち合わせがない外部サービス（ポータルサイトなど）は**ロゴを捏造せず**、
ピクトグラムのままにする。

### 4版が同じ座標で成立するように組む

ここが実際に詰まるところ。**版によってノードの高さが違う。**

| 版 | 中心から上 | 中心から下（ラベル含む） |
|---|---|---|
| Cards | 58 | 58 |
| ActionRow | 52 | 約 110 |
| LogoSeal / IconsV2 | 64 | **約 164** |

- **左右のポートはどの版も中心の高さに揃う**ので、横向きのエッジはそのまま使える
- **行間は一番背の高い版に合わせる。** 行の中心距離は **280px** 取る。
  Cards だけ見て 196px で組むと、LogoSeal にした瞬間にラベルが下の行へ重なる
- 記録層のチップと、小さな入力元は版を切り替えても箱のままにする（`plain: true`）

## 7. 図の中に「主張パネル」を置くか

ClaimIntake には「判定の非対称」パネル（AI P2 / ルール P1 / 現在値 P1）を図の中に置いた。
これは**図の山場**だが、[3] で右に現場を並べると**同じことを2回言う**ことになる。

→ **埋め込み用にパネルを外せるフラグ（`hidePanel`）を用意しておく。**
単体で見せるときは出し、資料に埋めるときは消す。

---

## 8. できたかどうかの検算

| 検算 | |
|---|---|
| 主系列が左から右に一直線に読めるか | 折れていたら並べ替える |
| 主体の色が図全体で一貫しているか | 同じ主体が2色になっていないか |
| 通らない経路が残っているか | きれいすぎる図は嘘 |
| 記録層がフローと違う見た目か | 同じ形だと流れに見える |
| 実測でない数字に断りがあるか | [1] の票の §6 と照合する |
| 縮小しても主系列が追えるか | [3] で必ず縮小される。0.6倍で撮って見る |
| **4版すべてで撮ったか** | Cards だけ見て組むと LogoSeal で行が重なる（§6） |

---

## 9. [3] への引き渡し票

```markdown
## 1. 図
コンポジションID / 工程数 / 尺。版は Cards / LogoSeal / IconsV2 / ActionRow の4つ（規定）

## 2. この図が語れないこと
| 語れること | 語れないこと |
芯（[1]§1）と重なる行に印を付ける。← [3] はここから要素を立てる

## 3. 図が既に言っていること
図の中に置いた主張（パネル、注記）の一覧。
[3] で同じことを言わないため。外せるフラグがあるなら書く。

## 4. 余白
縮小したときどこが空くか。0.6倍で撮ったキャプチャを添える。

## 5. 縮小の限界
何倍まで読めるか。地図として使うなら何倍まで許容できるか。
```

### 埋まっている例（ClaimIntake）

- **語れないこと**: 当事者が何を見ているか / 何秒かかるか /
  **ルールが上げなかったら何が起きるか** ← 芯と重なる
- **図が既に言っていること**: 判定の非対称パネル（`hidePanel` で外せる）
- **縮小の限界**: 0.59倍でノード名が読める。0.26倍は地図としてのみ
