# AgentFlowClaimIntake 設計メモ

`farleap/tenant-claim-intake-demoapp`（入居者通報の受付と判定の PoC）を図解するコンポジションの設計。
コンポジション名は暫定で `AgentFlowClaimIntake`。

このファイルは実装が進むたびに更新する。構造を変えたら「変更履歴」に1行追加すること。

## 1. この図で何を伝えるか

demoapp の README が主題をはっきり書いている。

> 商談の主題は「AI が判定します」ではなく **「AI が間違えたときにどう担保するか」**。

つまり、この図は**処理が流れる様子**を見せるものではない。見せるべきは次の3つ。

1. **判定の非対称**: 昇格は決定論のルールが強制し、降格は人しかできない
2. **AI の生出力を書き換えない**: ルールが上書きするのではなく、両方が別々に残る
3. **痕跡が消えない**: `inquiry_events` は追記のみ。`update` / `delete` を実装していない

既存の `AgentFlowInquiry` は「問い合わせが流れていく」図だったが、こちらは
**「AI とルールと人の三者が、それぞれ何を決められて何を決められないか」の図**になる。

## 2. 実装から読み取った構造

### チャネルと縫い目

すべてのチャネルが最終的に同じ2関数を通る（`docs/architecture.md` §2）。

```
POST /api/intake/text   ─┐
POST /api/intake/voice  ─┼→ intake() → conversations + turns + attachments
（予定）LINE webhook    ─┘        ↓
                            runJudgePipeline()
                                 ↓
                       judge() = LLM → セーフティルール → kind整合 → 人確認強制
                                 ↓
              inquiries（現在値）+ judgments（履歴）+ inquiry_events（追記のみ）
                                 ↓
                       runWorkPipeline()（2段目、応答後）
```

音声だけ受付と判定が別リクエストに分かれる。`/api/intake/voice` は STT までで応答し、
判定は `/api/intake/voice/judge` が別途呼ぶ。文字起こしが返った時点で通報者の画面を先に進めるため。

### 1段目（判定）の後処理は順序が固定

`resolveJudgment` の4手順（`docs/architecture.md` §3）。

1. セーフティルール適用。**ルールと AI の強い方を採る**ので、ルールが弱くても降格しない
2. kind 整合（`availability` / `viewing` / `contract` は `inquiry` に倒す）。ただし urgency の P3 固定はルール未発火のときだけ
3. `confidenceLevel` を数値に写す（high 0.9 / medium 0.65 / low 0.35）
4. `requiresHumanReview` を強制（low または P1）

### セーフティルール（決定論・LLM 不使用）

`src/domain/safety-rules.ts` に5本。

| id | 内容 | 昇格先 |
|---|---|---|
| `SAFETY_GAS_ODOR` | ガス臭・焦げ臭・煙 | P1 |
| `SAFETY_ELECTRIC` | 感電・漏電・火花・コンセントの焦げ | P1 |
| `SAFETY_WATER_SPREADING` | 天井からの漏水・階下への被害・被害拡大中 | P1 |
| `SAFETY_LOCKOUT` | 施錠不能 | P1 |
| `SEASONAL_HVAC` | 酷暑期・厳冬期の空調喪失（文脈変数の実装例） | P1 |

`SafetyRule.escalateTo` の型が `'P1' | 'P2'` しかないので、**降格ルールを書く場所が無い**。

### 2段目（業務判断）とガードレール

`runWorkPipeline` が責任区分候補・業務パラメータ・NextAction 候補を出し、
`src/domain/guardrails.ts` の G1〜G5 が**追加と制止のみ**を行う。

| id | 内容 |
|---|---|
| G1 | P1 案件に callback が無ければ追加する |
| G2 | 実行を阻む要素を `blockedBy` として付ける（削除ではない） |
| G3 | 借主過失候補は要確認を立てる |
| G4 | escalate 等を削らない。**「削る操作を実装しない」という構造で担保** |
| G5 | 最初の時間依存 action 1件に SLA 期限を写す |

G4 が「実装しないことで担保する」形になっているのは、`inquiry_events` に
`update` / `delete` を作らないのと同じ思想。図でもこの2つは同じ表現で扱う。

## 3. 論理構造

```
                      ┌──── 決定論（LLM を使わない）────┐
                      │                                │
 入居者 ──▶ 受付 ──▶ 文字起こし ──▶ AI判定 ──▶ セーフティルール ──▶ 記録
 (音声/テキスト)      (音声のみ)    (1段目)      5本・昇格のみ        │
   ▲  LINE(予定)                       │                            │
   │                                   ▼                            ▼
   │                            業務判断(2段目) ──▶ ガードレール ──▶ 記録
   │                            NextAction候補     G1〜G5(追加/制止)  │
   │                                                                 │
   └────────── 一次回答 ◀── 担当者 ◀───────────────────────────────┘
                              │ 降格は理由必須
                              └──▶ CSV出力（urgency_ai と fired_rule_ids を含む）
```

## 4. 画面レイアウト（1920x1080）

3つの帯と、右端の記録層で構成する。

```
[StepBar]                                                        [Legend]

 ┌── 入口 ──┐  ┌─────── CLAIM INTAKE RUNTIME ────────┐  ┌── 記録層 ──┐
 │ 入居者    │  │ ┌──────┐  ┌────────┐               │  │ 会話        │
 │ 音声/text ├──┼▶│ 受付  ├─▶│文字起こし│               │  │ conversations│
 └──────────┘  │ └──────┘  └────┬───┘               │  │ turns       │
 ┌ ─ ─ ─ ─ ┐   │                │                   │  ├─────────────┤
 │LINE(予定)├┄┄┼▶               ▼                   │  │ judgments   │
 └ ─ ─ ─ ─ ┘   │        ┌──────────┐  ┌──────────┐  │  │ AI生出力・履歴│
               │        │ AI判定    ├─▶│セーフティ │  │  ├─────────────┤
               │        │ 1段目 LLM │  │ルール 5本 │  │  │ inquiries   │
               │        └────┬─────┘  └────┬─────┘  │  │ 現在値       │
               │             │             │        │  ├─────────────┤
               │        ┌────▼─────┐  ┌────▼─────┐  │  │work_judgments│
               │        │業務判断   ├─▶│ガードレール│  │  ├─────────────┤
               │        │2段目 LLM  │  │ G1〜G5   │  │  │inquiry_events│
               │        └──────────┘  └──────────┘  │  │ 追記のみ     │
               └──────────────────┬──────────────────┘  └─────────────┘
                                  │
                          ┌───────▼────────┐
                          │ 担当者          │──▶ CSV出力
                          │ 降格は理由必須   │
                          └────────────────┘
```

- **記録層を右端に常設する**。ステップごとに該当テーブルが光り、`inquiry_events` は行が
  増えていく表現にする。「痕跡が消えない」を、ビートではなく画面に居続けるもので示す
- **決定論のノード（セーフティルール / ガードレール）を AI ノードの隣に並べる**。
  AI の右に必ず決定論が来る形にして、「AI の出力はそのまま通らない」を配置で伝える
- LINE は破線の「予定」ノード。README が未実装かつ設計済みと書いているので、そのとおり描く

## 5. 配色

demoapp 自身の設計判断を踏襲する（`docs/architecture.md` §8）。

> 「ルール昇格」タグは色ではなく `ink` 面 + 白文字で立てる。AI でも人でもない第3の主体を、
> 新しい色を発明せずに最強コントラストで示すため。

| 主体 | 色 | 対象 |
|---|---|---|
| 入力（入居者から） | シアン | 入居者、受付、文字起こし |
| AI の推論 | バイオレット | 1段目 AI判定、2段目 業務判断 |
| **決定論のルール** | **白 / ink（無彩色・最強コントラスト）** | セーフティルール、ガードレール |
| 人の判断 | オレンジ | 担当者、override |
| 記録 | グリーン | 記録層の各テーブル |
| 参照・非同期・予定 | グレー破線 | LINE（予定）、2段目の非同期起動 |

ルールだけ色相を持たないことで、「AI でも人でもない第3の主体」が図の上でも浮く。

## 6. タイムライン（案: 7ステップ x 4秒 = 28秒）

| step | 秒 | 内容 | 光るもの |
|---|---|---|---|
| 1 受付 | 0-4 | 音声かテキストで通報が届く | 入居者、受付、会話テーブル |
| 2 文字起こし | 4-8 | Private Blob に保存し STT にかける | 文字起こし、会話テーブル |
| 3 AI判定 | 8-12 | 1段目 LLM が緊急度とカテゴリを構造化出力（**AI は P2 と言う**） | AI判定、judgments |
| 4 ルール昇格 | 12-16 | `SAFETY_GAS_ODOR` が発火し **P1 に強制昇格**。AI の生出力は書き換えない | セーフティルール（白）、inquiries、judgments |
| 5 業務判断 | 16-20 | 2段目が NextAction 候補を出し、G1〜G5 が追加と制止のみ行う | 業務判断、ガードレール、work_judgments |
| 6 人の確認 | 20-24 | 担当者が一覧から詳細へ。**降格するなら理由が要る** | 担当者、inquiries、inquiry_events |
| 7 出口 | 24-28 | CSV に `urgency_ai` と `fired_rule_ids` が並んで出る | CSV、記録層すべて |

**step 4 がこの図の山場**。ここだけ演出を足す。

- AI の出力「P2」とルールの結論「P1」を同時に出し、**両方が残る**ことを見せる
- 上書きのアニメーション（AI の値が P1 に書き換わる）は**作らない**。それは実装と違う
- 「強い方を採る」を、2つの値が並んで片方に印が付く形で表す

## 7. AgentFlowInquiry との違い

| | AgentFlowInquiry | AgentFlowClaimIntake |
|---|---|---|
| 題材 | 業務フローの構想 | 実装済み PoC の構造 |
| 主役 | 問い合わせが流れる経路 | AI・ルール・人の権限の非対称 |
| 人の役割 | 判断基準を調整して次に効かせる | その場で降格する（理由必須） |
| 決定論の扱い | 出てこない | **主役の一角**。独立したノードで色も分ける |
| 記録 | 出てこない | 右端に常設し、追記のみを可視化 |

両方を残す。前者は「これから作るもの」、後者は「もう動いているもの」を指すので用途が違う。

## 8. 決定事項

| 項目 | 決定 |
|---|---|
| ステップ数 | 7ステップ x 4秒 = 28秒（840フレーム） |
| 山場の演出 | AI とルールの2値を並べる専用パネルを作る（§6 のとおり） |
| 音声の細部 | 出す。受付と判定が別リクエストである点はエッジの注記、追加質問はノードで表す |
| ベース | カード主体の `AgentFlowInquiry`（`AgentFlowInquiryIcons` ではない） |

## 9. 実装メモ

| ファイル | 内容 |
|---|---|
| `src/AgentFlowClaimIntake/constants.ts` | グリッド、ノード16個、エッジ12本、配色、パネル定義、タイムライン |
| `src/AgentFlowClaimIntake/index.tsx` | 図の描画、直角ルーティング、判定の非対称パネル、ステップバー、凡例 |

- **`tone` でカードの見た目を決める**（`input` / `ai` / `rule` / `human` / `record` / `planned`）。
  `rule` だけ色相を持たず白で立つ
- **通らない経路は `step: null`**。LINE（未実装）と追加質問（P1 では聞かない）が該当し、
  破線で常に非アクティブのまま置かれる。シナリオが P1 のガス臭なので、追加質問は
  仕様どおり発火しない。存在するが今回は通らない、を見た目で区別している
- **記録層へのエッジは引かない**。5つのチップが該当ステップで点灯するだけにした。
  ノードごとに線を引くと図の端から端まで5本走って読めなくなるため
- **`inquiry_events` は全ステップで点灯する**。追記のみで痕跡が消えないことを、
  ビートではなく点きっぱなしで示す
- 見出しは7文字以上のとき 25px から 20px に落とす（「セーフティルール」がカード幅に収まらないため）
