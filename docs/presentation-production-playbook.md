## 全体の順番

```
1  芯を1文にする
2  俯瞰（フロー図）をデータとして作る
3  「この図が語れないこと」を書き出す      ← ここが分岐点
4  語れないことごとに、要素を1つ立てる
5  場所の予算を測る
6  重複を潰す
7  変えていないことを機械で示す
```

**3が要**。ここを飛ばすと「なんとなく賑やかな図」になり、足した要素が何のために
あるのか自分でも言えなくなる。逆にここさえ書ければ、4以降はほぼ機械的に進む。

---

## 1. 芯を1文にする

**商談で本当に聞かれることを1文にする。** 作り手が言いたいことではない。

ClaimIntake の場合：

> ❌ AIが通報の緊急度を判定します
> ⭕️ **AIが間違えたとき、どう担保するのか**

この1文が、以降のすべての判断の基準になる。要素を足すか迷ったら
「これは芯に効くか」で決める。効かないなら足さない。

芯は題材の実装から拾う。ClaimIntake なら、実装が
「昇格はルールが強制し、降格は人だけができる」「AIの出力を書き換えない」
「記録は追記のみ」という形をしていた。**実装がすでに答えを持っていた**ので、
それを言語化しただけ。

---

## 2. 俯瞰（フロー図）をデータとして作る

図はコードで持つ。効いた作法は4つ。

| 作法 | なぜ |
|---|---|
| **座標を2箇所に書かない** | ノード位置とエッジの経由点を同じグリッド定数から導く。これを最初からやった図は、ノードサイズを何度変えてもエッジ側を触らずに済んだ |
| **通らない経路を消さない** | 未実装の経路も、条件が合わず今回通らない工程も破線で残す。実装にあるものを図から消すと図が嘘になる |
| **決定論のルールに色相を与えない** | AIでも人でもない第3の主体は白（無彩色・最強コントラスト）で立てる。題材のアプリ自身の設計判断を借りている |
| **上書きのアニメーションを作らない** | ルールがAIの値を書き換える演出は、実装が「書き換えない」設計である以上、嘘になる。2つの値を並べて片方に印を付ける |

下の2つは**演出の都合で実装を裏切らない**という話で、芯が「担保」である以上、
ここで嘘をつくと商材そのものが嘘になる。

---

## 3. 「この図が語れないこと」を書き出す

フロー図は**三人称の俯瞰**なので、構造的に映せないものがある。表にする。

| 語れること | 語れないこと |
|---|---|
| どこからどこへ流れるか | 当事者が何を見ているか |
| どの工程に人が挟まるか | その工程が何秒かかるか |
| ルールが緊急度を上げること | **上げなかった場合に何が起きるか** |

**芯と重なる行に印を付ける。** ClaimIntake では3行目がそれだった。
以降、そこを埋める要素を最優先で作る。

---

## 4. 語れないことごとに、要素を1つ立てる

1つの「語れないこと」に、1つの要素。兼用させない。

| 語れないこと | 立てる要素 | 設計の勘所 |
|---|---|---|
| 当事者が何を見ているか | **現場**（一人称の画面） | 抽象を現物にする。「AIがP2と言った」は抽象だが、JSONに `"P2"` と書いてあるのを見せると現実になる |
| 失敗したときの損失 | **反実仮想**（2本の結末を並べる） | 「〜がなければ」を仮定と明示する。危険の発生や見落としを断定しない |
| 速さ | **経過時間**（走る時計） | シナリオ値であることを画面に書く。実測でないものを実測に見せない |
| 痕跡が消えないこと | **追記ログ**（積まれて消えない点） | 一度出たものが最後まで残る、という形そのものが主張になる |
| （全体像が要らない場面） | **文字主体の版** | 図をやめる。遠くから読めるかわりに経路は語らない |

### 現場の作り方

**実装の語彙をそのまま使う。** `urgency_ai` `fired_rule_ids` `judgments.raw` のような
実際のフィールド名が画面に出ていると、作り話に見えなくなる。逆に、
実装に無い画面（実アプリの管理画面そのものなど）は再現せず、
「説明用の画面再構成」と断る。

### 要素を足す単位

**既存のコンポジションを変えず、別コンポジションとして足す。**
案を消さずに残せるので、あとで並べて比べられる。
`zod` スキーマと `defaultProps` を付けておくと、Studio の props パネルから
登録していない組み合わせも試せる。

## 5. 場所の予算を測る

**1920×1080 は思ったより狭い。** 早めに実測する。

今回の実測値：

- 左右2カラムに割ると、**縦に積める余地は下に1帯ぶんしかない**。
  反実仮想と追記ログは場所を取り合うので排他にした
- 1920×1080 の作りものを2枚入れると、**両方が読める大きさには収まらない**。
  どちらかを主役、もう一方を地図まで小さくするしかない
- 縮小は**思ったより効く**。0.59倍でもノード名は読めた。
  地図に徹させるなら 0.26 倍まで落として問題ない

**主役をどちらにするかを先に決める。** 決めずに両方大きくしようとすると必ず破綻する。

---

## 6. 重複を潰す

要素を足していくと、**同じことを複数の場所で言い始める。** 今回は「47秒」が
時計・現場の出口・反実仮想の3箇所に出た。

対処は2段階。

1. **表示の重複**は、出す側ではなくレイアウト側で判断する。
   「時計を出しているなら出口では言わない」の判断を画面に持たせると、
   画面がヘッダの事情を知ることになる
2. **値の重複**は、事実を1箇所に集めて構造で防ぐ。
   受付番号・AIの値・ルールID・経過秒を1ファイルに置き、
   経過秒は最後のイベントから引く形にすると、2箇所に書きようがなくなる

規律（「気をつける」）で防ごうとしないほうがよい。実際に一度やらかしている。

## 7. 変えていないことを機械で示す

コードで図を持つ最大の利点。**同じフレームのPNGを `cmp` でバイト比較**する。

```sh
pnpm exec remotion still <Id> before.png --frame=420 --gl=swangle
# ...変更...
pnpm exec remotion still <Id> after.png --frame=420 --gl=swangle
cmp before.png after.png
```

運用上の注意が3つ。

- **レンダーの前後でソースの `md5` を取る。** 一度、レンダー実行中にソースを
  書き換えて偽の差分を出した。結果だけ見るとリグレッションと区別がつかない
- **各工程の中間フレームを撮る**（60, 180, 300, 420, 540, 660, 780）。
  工程の境目だけだと遷移中の絵しか見ない
- **既定のプリセットに含まれない分岐も撮る。** `--props` を渡せばよい。
  条件分岐を組み替えたときは、通常の描画が一致していても意味が変わっていることがある

## 実装の型（Remotion）

### 既存のものを縮めて埋める

```tsx
<div style={{ width: W, height: H, transform: `scale(${s})`, transformOrigin: "top left" }}>
  <既存のコンポジション />
</div>
```

中身が `useCurrentFrame()` だけで状態を決めていれば、**同期のコードは要らない。**
縮小して置くだけで進行が勝手に揃う。これが効くので、
「フロー図＋何か」の構成は驚くほど安く作れる。

### 組み合わせを props にする

案を1つずつコンポジションに切ると数ばかり増えて、組み合わせを試せない。
`zod` スキーマ＋プリセットにしておくと、Studio 上で自由に試せる。

### 環境の罠

| 事象 | 対処 |
|---|---|
| headless Chromium が WebGL に失敗する | `--gl=swangle`（`--gl=angle` では不十分） |
| 動画の pix_fmt が `yuvj420p` になる | `--image-format=png` と `--pixel-format=yuv420p` を**両方** |
| 親に `opacity` を掛けると背後のSVGが透ける | 背景と枠は不透明のまま、中身だけ内側の wrapper で掛ける |
| `position: absolute` の部品を絶対配置で囲むとオフセットが二重 | 逆オフセットか、同じ座標系の `relative` の帯 |
| 日本語が1文字だけ次行に落ちる | 幅と字数を手で合わせる。自動では解けていない |

## 分かれ道と、そのときの決め方

今回くり返し出てきた判断。

| 迷い | 決め方 |
|---|---|
| この要素を足すか | 3で書いた「語れないこと」のどれかを埋めるか。埋めないなら足さない |
| どちらを主役にするか | 芯に近いほうを大きくする。地図は小さくてよい |
| 足すか、置き換えるか | **足す**。既存を消さずに別コンポジションにして、あとで並べて比べる |
| 文言を共有するか直書きするか | **値は共有、言い回しは直書き。** データのスロット（P2, 47）は1箇所から引き、文章は読みやすさを優先してその場に書く |
| 縮小して読めるか不安 | 実際に撮って見る。予想はよく外れる |

## 予想が外れたこと

正直に残しておく価値があるもの。

1. **「縮小すると読めなくなるから簡略版が要る」→ 要らなかった。**
   0.59倍でもノード名は読めた。地図用の別バージョンを作らずに済んだ
2. **「要素は足すほど伝わる」→ 3箇所で同じことを言い始めた。**
   足すたびに「既にどこかで言っていないか」を確認する工程が要る
3. **「経過時間と追記ログは別々の要素」→ 1つにまとめたほうが良かった。**
   場所が足りないことから横軸を時間にしたら、速さも追記も同じ帯で言えた上に、
   **待ち時間がどこにあるか**（0〜22秒に6件、そこから47秒まで空く）まで見えた。
   制約から入ったほうが良い設計になることがある

## 人に渡すとき

他の人やエージェントにプロトタイピングを任せるなら、渡すのは**仕様書ではなく問題**。
[`presentation-site-brief.md`](./presentation-site-brief.md) がその形で、構成は：

1. 解きたい問題（「語れないこと」の表を含む）と、決まっていないこと
2. 題材の中身（芯と、それを支える実装上の主張）
3. 環境と作法、出力を変えていないことの示し方
4. 踏んだ罠
5. 進め方
6. **補足：既に試した分** ← 最後に置き、「自分の案を出してから読め」と明記する

6を先頭に置くと発想が引きずられる。**既にあるものは、答え合わせとして最後に読ませる。**

## 残っている宿題

1. **触って試せる要素。** 定型文を数個から選ぶと発火するルールが変わる程度のもの。
   「説明された」が「試した」に変わるはずだが、動画では作れない。サイトが要る
2. **降格のシナリオ。** 判定の非対称の片側（ルールによる昇格）しか描けていない。
   AIがP1と言い、人が理由を書いて下げる側を見せると、主張が両側そろう
3. **最終的な出力形式。** 動画1本なのか、動画を埋めた1枚サイトなのか
